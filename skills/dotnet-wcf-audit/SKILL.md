# WCF Framework Specialty Audit

## Shared Grabber Index References

- By default, use shared/DOTNET_AUDIT_GRABBER_INDEX.md as this Skill's base retrieval index
- By default, use shared/DOTNET_SINK_REFERENCE.md as this specialty's sink type definition and trace-gate validation baseline
- By default, follow the common execution standard in `skills/shared/DOTNET_AUDIT_EXECUTION_STANDARD.md` (two-phase determination, fail-close determination, testing requirements)
- Enumeration must at least cover WCF-related entry definitions, binding conversions, pre-controls, sensitive operations, and security configuration grabbers
- If the project has framework secondary encapsulation, unified extension methods, a platform base, or a host wrapper layer, they must be added to the in-project grabbers section of the output
- When this Skill's specialty enumeration rules are more detailed than the shared index, this Skill prevails, but the shared index's base coverage must not be reduced

## Input Dependencies

- Required: `source_path`
- Optional: `route_mapping/routes_{timestamp}.md` and `route_mapping/params_{timestamp}.md` (if already generated by `dotnet-route-mapper`, used to align service operations, message parameters, and `route_id`)
- Optional: `auth_audit/auth_mapping_{timestamp}.md` (if service contract authorization, anonymous operations, and resource ownership boundaries need to be aligned)
- Optional: `route_tracer/{route_id}/trace_{timestamp}.md` and `route_tracer/{route_id}/trace_summary_{timestamp}.md` (if message processors, serialization chains, and specific side-effect paths need to be cross-referenced)

## Key Checks

- BasicHttpBinding, WSHttpBinding, NetTcpBinding, NetNamedPipeBinding, security modes, transport protection, and message-level protection configuration
- NetDataContractSerializer, DataContractSerializer, XmlSerializer, XmlReader, XDocument, MessageContract, KnownTypes, BinaryMessageEncoding, and message body parsing boundaries
- ServiceAuthorizationManager, PrincipalPermission, custom message inspectors, behavior extensions, identity impersonation, and client certificate validation
- MEX metadata exposure, svc debug pages, IncludeExceptionDetailInFaults, detailed faults, diagnostic tracing, and service manifest leakage
- State boundaries in SOAP headers, WS-Security, sessions, reliable messaging, transactions, callback contracts, and duplex communication
- Legacy .NET Framework hosts, IIS/WAS, self-hosted Windows Services, port exposure, and protection strategy differences

## Enumeration Rules (Mandatory Refinement)

- Enumerate all ServiceContracts, OperationContracts, Bindings, BehaviorExtensions, MessageInspectors, ServiceAuthorizationManagers, PrincipalPermissions, and host configuration items
- Search with priority: BasicHttpBinding, WSHttpBinding, NetTcpBinding, NetNamedPipeBinding, security mode, IncludeExceptionDetailInFaults, serviceMetadata, mex, KnownType, NetDataContractSerializer, XmlReader, XDocument, DtdProcessing, XmlResolver, XmlSerializerFormat
- Enumerate SOAP headers, MessageContracts, transactions, reliable messaging, duplex callbacks, session instance modes, certificate validation, impersonation, and XmlResolver, DtdProcessing, XslCompiledTransform-related parsing configuration; record state retention and trust boundaries
- Enumerate web.config, app.config, self-hosting initialization code, and IIS/WAS host configuration; record debug switches, metadata exposure, binding addresses, and transport protection differences
- For each service operation record: binding, authentication method, serializer, message inspector, exception/fault output, host environment, and reachability

## Barrier Verification Matrix (Mandatory)

Assess against the fail-close three-tier standard in `DOTNET_AUDIT_EXECUTION_STANDARD.md`:

| Tier | Check Item | Pass Criteria | Failure Degradation |
|------|--------|----------|----------|
| Tier 1 | Service endpoint exists and is reachable | A ServiceContract/OperationContract exists and the host (IIS/WAS/self-hosted) exposes an accessible endpoint | BLOCKED → no reachable WCF endpoint; the specialty is deprioritized |
| Tier 2 | Binding/serialization has security issues | BasicHttpBinding without transport protection, NetDataContractSerializer/XmlSerializer deserialization risks, XmlResolver/DtdProcessing unsafe | BLOCKED → binding is secure and serialization configuration is risk-free; conclusion degraded |
| Tier 3 | Authorization/metadata exposure is exploitable | ServiceAuthorizationManager/PrincipalPermission missing, or MEX/introspection/fault detailed information exposed in production | PARTIAL → only potential risks and verification steps are output |

## Two-Phase Determination Flow (Mandatory)

- **Phase 1 (Initial Screening Hit)**: WCF service endpoint + binding/serialization configuration + authorization/metadata exposure hit; output `Hit ID: M{hash}`.
- **Phase 2 (Refined Confirmation)**:
  1. Trace in reverse: ServiceContract → Binding → host configuration chain, confirming endpoint reachability;
  2. Verify BasicHttpBinding/WSHttpBinding security modes, NetDataContractSerializer/XmlSerializer deserialization risks, XmlResolver/DtdProcessing configuration;
  3. Assess ServiceAuthorizationManager/PrincipalPermission absence and MEX/fault detailed information exposure;
  4. If all three barrier tiers pass → `Confirmed Vulnerability`; if any fails → degrade per the matrix.

## Determination Rules and Priority (Mandatory)

1. **Confirmed Vulnerability**: endpoint reachable + binding/serialization unsafe + authorization missing/metadata exposed. Output `Confirmed Vulnerability`.
2. **Pending Confirmation**: endpoint/binding/authorization evidence partially exists, but the host environment or runtime configuration cannot be proven. Output `Pending Confirmation`.
3. **False Positive / No Risk**: endpoint unreachable or protected, binding has transport/message-level security enabled, serialization configuration is safe, authorization is complete, and metadata is not exposed. Output `False Positive` with determination basis.

## Testing Suggestions and Minimum Trigger Conditions (Mandatory)

- **Minimum Trigger Conditions**:
  - A WCF ServiceContract/OperationContract exists
  - The host (IIS/WAS/self-hosted) exposes the endpoint and it is reachable
  - Or BasicHttpBinding lacks transport protection, NetDataContractSerializer has a deserialization risk
  - Or ServiceAuthorizationManager is missing, MEX/fault detailed information is exposed
- **Test Case Suggestions**:
  - Happy Path: a normal SOAP request is processed through a secure binding and authorization, returning a correct response
  - Edge/Ambiguity: NetDataContractSerializer type confusion, XmlResolver DTD injection, IncludeExceptionDetailInFaults information leakage, impersonation over-privilege
- Each hit output appends `Hit ID: M{hash}` and `test_id: T{hash}` for traceability.

## Checkpoint Design (Mandatory)

- 🔴 **CHECKPOINT A (Endpoint and Binding Confirmation)**: must confirm service endpoints, Bindings, and message encoding configuration.
- 🔴 **CHECKPOINT B (Message Security Confirmation)**: must confirm transport/message-level security and certificate policies.
- 🔴 **CHECKPOINT C (Operation Chain Confirmation)**: must confirm the chain from OperationContract to downstream sensitive operations is closed.
- 🛑 **STOP**: if endpoint security and the call chain are not closed, the conclusion is degraded to `⚠️Pending Verification`.

## Executable Parameters and Output Templates (Mandatory)

- Audit conclusion level: `Confirmed` / `⚠️Pending Verification` / `Not Applicable` (choose exactly one; leaving blank is forbidden).
- Minimum evidence set: must include at least the five items `entry point`, `controllable parameters`, `key calls`, `security boundary`, `missing evidence`.
- Output file naming: uniformly use `{topic}_{timestamp}.md`, aligned with `IO_PATH_CONVENTION.md`.
- Softening wording is forbidden: e.g. "possibly at risk / worth noting / depends on the situation / very likely"; when evidence is insufficient, must explicitly write `⚠️Pending Verification` and the next follow-up confirmation action.

Minimal output snippet (directly reusable):

```md
- Audit conclusion level: Confirmed
- Minimum evidence set: entry point=...; controllable parameters=...; key calls=...; security boundary=...; missing evidence=none
- Next action: if gaps exist, supplement parameter propagation evidence for trace_id=...
```

## Failure and Degradation Branches (Mandatory)

| Trigger Condition | First-Line Handling | Fallback if Still Failing |
|---|---|---|
| Real host (IIS/WAS/self-hosted) cannot be located | Output identified bindings and configuration evidence | Conclusion degraded to `⚠️Environment-Dependent`; strong conclusions are forbidden |
| ServiceBehavior/Binding configuration sources incomplete | Enumerate both code configuration and config files | Missing items listed for follow-up confirmation and marked PARTIAL |
| Message inspector/authorization manager implementation unresolvable | Record interfaces, registration points, and candidate implementations | If it cannot be narrowed down, keep the candidate set and degrade |
| Only an unsafe switch found but no reachable operation evidence | Output configuration risk and impact scope | Do not output "confirmed exploitable"; risk notice only |

🔴 **STOP: when host and binding evidence is not closed, outputting a "confirmed exploitable" or P0 conclusion is forbidden.**

## Quality Gate & Assessment Consistency (Mandatory)

## Do NOT Do (Anti-Pattern Blacklist)

| # | Anti-Pattern | Why Not | Correct Approach |
|---|---|---|---|
| 1 | Treating framework default behavior as the project's real configuration | WCF often has environment overrides | Must give the project's actual configuration source |
| 2 | Only looking at contracts, ignoring the host | Risk validity depends on the exposure surface | Record contract, binding, and host together |
| 3 | Ignoring message inspector execution order | Protection effectiveness is easily misjudged | Output behavior extension/inspector order evidence |
