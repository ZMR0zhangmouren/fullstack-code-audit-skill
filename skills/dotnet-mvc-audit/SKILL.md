# ASP.NET MVC Framework Specialty Audit

## Shared Grabber Index References

- By default, use shared/DOTNET_AUDIT_GRABBER_INDEX.md as this Skill's base retrieval index
- By default, use shared/DOTNET_SINK_REFERENCE.md as this specialty's sink type definition and trace-gate validation baseline
- By default, follow the common execution standard in `skills/shared/DOTNET_AUDIT_EXECUTION_STANDARD.md` (two-phase determination, fail-close determination, testing requirements)
- Enumeration must at least cover MVC-related entry definitions, binding conversions, pre-controls, sensitive operations, and security configuration grabbers
- If the project has framework secondary encapsulation, unified extension methods, a platform base, or a host wrapper layer, they must be added to the in-project grabbers section of the output
- When this Skill's specialty enumeration rules are more detailed than the shared index, this Skill prevails, but the shared index's base coverage must not be reduced

## Input Dependencies

- Required: `source_path`
- Optional: `route_mapping/routes_{timestamp}.md` and `route_mapping/params_{timestamp}.md` (if already generated by `dotnet-route-mapper`, used to align Action entries, binding sources, and `route_id`)
- Optional: `auth_audit/auth_mapping_{timestamp}.md` (if anonymous entries, P0/P1 bucketing, and filter authorization boundaries need to be aligned)
- Optional: `route_tracer/{route_id}/trace_{timestamp}.md` and `route_tracer/{route_id}/trace_summary_{timestamp}.md` (if View/Redirect/File return chains need to be cross-referenced with specific side-effect paths)

## Key Checks

- Coverage relationships of Controller/Action-level authorization, global filters, Areas, ChildActions, FilterAttributes, and custom ActionFilters
- Model Binding, TryUpdateModel, Bind/BindNever, FromForm, JSON Patch, upload models, and over-posting risks
- Razor Raw / HtmlString, Layout, Partial, EditorTemplate, DisplayTemplate, TagHelper, ViewComponent, and the output boundaries of Controller Content / Json / hand-built HTML / JS
- Trust boundaries in TempData, ViewBag, ViewData, ModelState, ReturnUrl, partial view composition, error pages, and redirect chains
- Security impact of Anti-forgery, OutputCache, FileResult, Content-Disposition download names, content negotiation, and exception filters
- Configuration drift and compatibility-layer issues in projects mixing classic ASP.NET MVC with ASP.NET Core MVC

## Enumeration Rules (Mandatory Refinement)

- Enumerate all Controllers, Areas, Actions, ChildActions, Partial render points, ViewComponents, and custom FilterAttributes; record their route sources, authorization metadata, and view render targets
- Search with priority: Controller, ActionResult, TryUpdateModel, UpdateModel, Bind, BindNever, ValidateAntiForgeryToken, Html.Raw, HtmlString, Redirect, LocalRedirect, RedirectToAction, Content, Json, File, PartialView
- Enumerate ModelBinder, ValueProvider, ModelState modification points, upload models, complex object binding, collection binding, and JSON Patch entries; record which fields can be directly overwritten by the client
- Enumerate Razor View, Layout, Partial, EditorTemplate, DisplayTemplate, HtmlHelper, custom TagHelper, and ViewBag/ViewData/TempData data injection points; record output encoding and trust boundaries
- For each Action record: entry route, binding sources, pre-filters, view/return type, state-change capability, and whether it depends on legacy configuration or a compatibility layer

## Barrier Verification Matrix (Mandatory)

Assess against the fail-close three-tier standard in `DOTNET_AUDIT_EXECUTION_STANDARD.md`:

| Tier | Check Item | Pass Criteria | Failure Degradation |
|------|--------|----------|----------|
| Tier 1 | Controller/Action entry exists and mapping is complete | An unauthorized or anonymously reachable Controller/Action exists, and route mapping is complete and triggerable | BLOCKED → all entries have authorization coverage and mapping is complete; the specialty is deprioritized |
| Tier 2 | Binding/filter chain has a bypass | ModelBinding, TryUpdateModel, Bind/BindNever etc. have over-posting or field-overwrite bypasses | BLOCKED → binding chain is complete and filters have no bypass; conclusion degraded |
| Tier 3 | View/return surface has output security issues | Razor Raw/HtmlString/Content/Json/File return surfaces have unencoded output or sensitive information leakage | PARTIAL → only potential risks and verification steps are output |

## Two-Phase Determination Flow (Mandatory)

- **Phase 1 (Initial Screening Hit)**: Controller/Action entry + binding/filter chain + output surface hit; output `Hit ID: M{hash}`.
- **Phase 2 (Refined Confirmation)**:
  1. Trace in reverse: Controller/Action → filter chain → authorization policy chain;
  2. Verify the over-posting or field-overwrite conditions of ModelBinding, TryUpdateModel, Bind/BindNever;
  3. Assess the encoding boundaries and sensitive information leakage of Razor/Content/Json/File return surfaces;
  4. If all three barrier tiers pass → `Confirmed Vulnerability`; if any fails → degrade per the matrix.

## Determination Rules and Priority (Mandatory)

1. **Confirmed Vulnerability**: entry unauthorized-reachable + binding/filter bypass + return surface has a security issue. Output `Confirmed Vulnerability`.
2. **Pending Confirmation**: entry/binding/output surface evidence partially exists, but the authorization chain or encoding context cannot be proven. Output `Pending Confirmation`.
3. **False Positive / No Risk**: all entries have authorization coverage, the binding chain is complete with no bypass, and return surfaces are correctly encoded. Output `False Positive` with determination basis.

## Testing Suggestions and Minimum Trigger Conditions (Mandatory)

- **Minimum Trigger Conditions**:
  - An ASP.NET MVC Controller/Action exists
  - An unauthorized or anonymously reachable entry exists
  - Or the ModelBinding/filter chain has over-posting/bypass
  - Or the return surface has unencoded output/sensitive information leakage
- **Test Case Suggestions**:
  - Happy Path: a normal request is processed through the complete filter chain with correct authorization and binding
  - Edge/Ambiguity: ChildAction/Area filter coverage differences, BindNever and over-posting, Razor encoding context switching
- Each hit output appends `Hit ID: M{hash}` and `test_id: T{hash}` for traceability.

## Checkpoint Design (Mandatory)

- 🔴 **CHECKPOINT A (Controller Mapping Confirmation)**: must confirm Controller/Action and route mapping is complete.
- 🔴 **CHECKPOINT B (Binding and Filter Confirmation)**: must confirm ModelBinding, filters, and the authorization chain are in effect.
- 🔴 **CHECKPOINT C (Output Surface Confirmation)**: must confirm the security boundaries of View/Redirect/File return surfaces.
- 🛑 **STOP**: if mapping and the authorization chain are not closed, the conclusion is degraded to `⚠️Pending Verification`.

## Executable Parameters and Output Templates (Mandatory)

- Audit conclusion level: `Confirmed` / `⚠️Pending Verification` / `Not Applicable` (choose exactly one; leaving blank is forbidden).
- Minimum evidence set: must include at least the five items `entry point`, `controllable parameters`, `key calls`, `security boundary`, `missing evidence`.
- Output file naming: uniformly use `{topic}_{timestamp}.md`, aligned with `IO_PATH_CONVENTION.md`.
- Softening wording is forbidden: e.g. "possibly at risk / worth noting / depends on the situation / very likely"; when evidence is insufficient, must explicitly write `⚠️Pending Verification` and the next follow-up confirmation action.

Minimal output snippet (directly reusable):

```md
- Audit conclusion level: Confirmed
- Minimum evidence set: entry point=...; controllable parameters=...; key calls=...; security boundary=...; missing evidence=none
- Next action: if gaps exist, supplement parameter propagation evidence for trace_id=...
```

## Failure and Degradation Branches (Mandatory)

| Trigger Condition | First-Line Handling | Fallback if Still Failing |
|---|---|---|
| Action entry visible but filter chain incomplete | Output known filters and route evidence | Mark PARTIAL and list missing filter evidence |
| Binding risk exists but field overwrite scope unclear | Record visible DTO fields and binding sources | Degrade to Pending Confirmation; over-posting "confirmed" conclusions are forbidden |
| Output point exists but encoding context incomplete | Output Razor/return type and output points | Give only potential risks, no strong conclusion |
| Compatibility layer (legacy MVC / Core) boundary unclear | List evidence per environment with difference hypotheses | Degrade conclusion to Environment-Dependent |

🔴 **STOP: when any of the filter, binding, or output chains is missing, outputting a "confirmed exploitable" conclusion is forbidden.**

## Measured Test Cases and Pass Criteria (Mandatory)

- Each skill must maintain at least 2 typical test cases (happy path + one complex scenario), and annotate the case ID in the results.
- Each evaluation round must execute `full_test` for at least 1 case; if only `dry_run` is possible, `dry_run_reason` and a make-up test plan must be recorded.
- Pass criteria must simultaneously satisfy: `intent achieved`, `key evidence hit`, `output format compliant`; if any one is not met, "pass" must not be given.

## Quality Gate & Assessment Consistency (Mandatory)

- A minimal gate self-check must be executed before producing output: `input completeness`, `key evidence hit`, `output path valid` — all three must be PASS.
- If any of `key evidence missing`, `chain not closed`, `consistency_check_status=BLOCKED` holds, the conclusion must be degraded to `BLOCKED`; outputting "confirmed exploitable/deliverable" is forbidden.
- The report must explicitly record: `gate_status`, `blocked_reasons`, `recheck_action`, and be traceably aligned with the `quality/*` artifacts.

## Do NOT Do (Anti-Pattern Blacklist)

| # | Anti-Pattern | Why Not | Correct Approach |
|---|---|---|---|
| 1 | Only looking at Controllers, ignoring Views/Filters | The evidence chain breaks | Cover entries, filters, and output together |
| 2 | Classifying all HTML output issues as high-risk XSS | Context and encoding determine severity | Annotate the context and grade accordingly |
| 3 | Ignoring Anti-forgery conditional branches | CSRF conclusions are easily misjudged | Explicitly record token validation branches |

Output type mapping: AUTH, XSS, LOGIC, CFG, CSRF.
