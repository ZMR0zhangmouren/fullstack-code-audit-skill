# GraphQL Framework Specialty Audit

## Shared Grabber Index References

- By default, use shared/DOTNET_AUDIT_GRABBER_INDEX.md as this Skill's base retrieval index
- By default, use shared/DOTNET_SINK_REFERENCE.md as this specialty's sink type definition and trace-gate validation baseline
- By default, follow the common execution standard in `skills/shared/DOTNET_AUDIT_EXECUTION_STANDARD.md` (two-phase determination, fail-close determination, testing requirements)
- Enumeration must at least cover GraphQL-related entry definitions, binding conversions, pre-controls, sensitive operations, and security configuration grabbers
- If the project has framework secondary encapsulation, unified extension methods, a platform base, or a host wrapper layer, they must be added to the in-project grabbers section of the output
- When this Skill's specialty enumeration rules are more detailed than the shared index, this Skill prevails, but the shared index's base coverage must not be reduced

## Input Dependencies

- Required: `source_path`
- Optional: `route_mapping/routes_{timestamp}.md` and `route_mapping/params_{timestamp}.md` (if already generated by `dotnet-route-mapper`, used to align public operations, variable bindings, and `route_id`)
- Optional: `auth_audit/auth_mapping_{timestamp}.md` (if resolver authorization, anonymous entries, and resource ownership boundaries need to be aligned)
- Optional: `route_tracer/{route_id}/trace_{timestamp}.md` and `route_tracer/{route_id}/trace_summary_{timestamp}.md` (if resolvers need to be cross-referenced with downstream SQL/SSRF/file/template side-effect chains)

## Key Checks

- Resolver-level authorization, field-level authorization, schema stitching, federation, tenant context, and authorization consistency in batch queries
- Impact of Query, Mutation, and Subscription parameter binding, input objects, aliases, fragments, variables, and default values on business validation
- Introspection, schema exposure, playground, Banana Cake Pop, persisted queries, complexity limits, depth limits, and batch query boundaries
- Custom scalars, DataLoader, cache keys, batch processors, N+1 optimization, and over-privileged data reuse risks
- GraphQL upload, subscription connections, WebSocket authentication, error returns, debug information, and tracing extension exposure
- Whether resolvers further call HttpClient.SendAsync / GetAsync, HttpWebRequest / WebRequest.Create, files, commands, templates, database RawSQL, or background jobs, forming compound risks

## Enumeration Rules (Mandatory Refinement)

- Enumerate Queries, Mutations, Subscriptions, field resolvers, DataLoaders, schema configuration, authorization middleware, complexity limiters, and introspection switches
- Search with priority: AddGraphQL, AddQueryType, AddMutationType, AddSubscriptionType, Authorize, UsePaging, UseFiltering, UseSorting, DataLoader, UploadType, Introspection
- Enumerate input objects, variables, fragments, aliases, batch queries, persisted queries, uploads, subscription connections, and WebSocket handshake logic; record field-level validation and tenant constraints
- Enumerate playground, Banana Cake Pop, schema export, error extensions, tracing, debug output, and introspection configuration; record whether they are exposed in production
- For each high-risk resolver record: field name, call type, authorization conditions, input objects, batch behavior, downstream call types, and compound risk chains

## Barrier Verification Matrix (Mandatory)

Assess against the fail-close three-tier standard in `DOTNET_AUDIT_EXECUTION_STANDARD.md`:

| Tier | Check Item | Pass Criteria | Failure Degradation |
|------|--------|----------|----------|
| Tier 1 | Schema operations exist and are reachable | Query/Mutation/Subscription exist and are externally reachable (including playground/introspection) | BLOCKED → no reachable GraphQL endpoint; the specialty is deprioritized |
| Tier 2 | Authorization/complexity control has a bypass | Resolver/field-level authorization missing, or depth/complexity limits bypassable | BLOCKED → authorization and complexity control are complete; conclusion degraded |
| Tier 3 | Downstream compound risk reaches sensitive operations | Resolvers call database/file/command/template/SSRF sinks without business authorization | PARTIAL → only potential risks and verification steps are output |

## Two-Phase Determination Flow (Mandatory)

- **Phase 1 (Initial Screening Hit)**: GraphQL schema/resolver + authorization/complexity configuration + downstream call chain hit; output `Hit ID: M{hash}`.
- **Phase 2 (Refined Confirmation)**:
  1. Trace in reverse: Query/Mutation/Subscription → Resolver → downstream calls chain;
  2. Verify field-level authorization, depth/complexity limits, and introspection exposure conditions;
  3. Assess the authorization boundaries and compound risks of resolver downstream calls (SQL/file/command/template/SSRF);
  4. If all three barrier tiers pass → `Confirmed Vulnerability`; if any fails → degrade per the matrix.

## Determination Rules and Priority (Mandatory)

1. **Confirmed Vulnerability**: schema reachable + authorization/complexity bypass + downstream compound risk unauthorized. Output `Confirmed Vulnerability`.
2. **Pending Confirmation**: schema/authorization/downstream call evidence partially exists, but field-level authorization or complexity limits cannot be proven. Output `Pending Confirmation`.
3. **False Positive / No Risk**: GraphQL endpoint unreachable or protected, all resolvers authorized, complexity limits strict, downstream calls have business authorization. Output `False Positive` with determination basis.

## Testing Suggestions and Minimum Trigger Conditions (Mandatory)

- **Minimum Trigger Conditions**:
  - A GraphQL endpoint exists (Query/Mutation/Subscription)
  - The endpoint is externally reachable, or introspection/playground is exposed in production
  - Or resolver/field-level authorization checks are missing
  - Or depth/complexity limits are bypassable
- **Test Case Suggestions**:
  - Happy Path: a normal GraphQL query is processed through authorization and complexity limits, returning a correct response
  - Edge/Ambiguity: nested query depth attack, batch query alias bypass, introspection sensitive field exposure, resolver downstream SSRF/SQL injection
- Each hit output appends `Hit ID: M{hash}` and `test_id: T{hash}` for traceability.

## Checkpoint Design (Mandatory)

- 🔴 **CHECKPOINT A (Schema Boundary Confirmation)**: must confirm the exposure surface and authorization boundaries of Query/Mutation/Subscription.
- 🔴 **CHECKPOINT B (Resolution Chain Confirmation)**: must confirm resolver parameter sources and controllable chains to downstream sinks.
- 🔴 **CHECKPOINT C (Protection Strategy Confirmation)**: must confirm protections such as depth/complexity/field-level authorization.
- 🛑 **STOP**: if schema boundaries and the resolution chain are not closed, a "risk under control" conclusion is not allowed.

## Executable Parameters and Output Templates (Mandatory)

- Audit conclusion level: `Confirmed` / `⚠️Pending Verification` / `Not Applicable` (choose exactly one; leaving blank is forbidden).
- Minimum evidence set: must include at least the five items `entry point`, `controllable parameters`, `key calls`, `security boundary`, `missing evidence`.
- Output file naming: uniformly use `{topic}_{timestamp}.md`, aligned with `IO_PATH_CONVENTION.md`.
- Softening wording is forbidden: e.g. "possibly at risk / worth noting / depends on the situation / very likely"; when evidence is insufficient, must explicitly write `⚠️Pending Verification` and the next follow-up confirmation action.

Minimal output snippet (directly reusable):

```md
- Audit conclusion level: Confirmed
- Minimum evidence set: entry point=...; controllable parameters=...; key calls=...; security boundary=...; missing evidence=none
- Next action: if gaps exist, supplement parameter propagation evidence for trace_id=...
```

## Failure and Degradation Branches (Mandatory)

| Trigger Condition | First-Line Handling | Fallback if Still Failing |
|---|---|---|
| Resolver authorization annotations exist but runtime policies invisible | Output annotation and policy reference evidence | Mark PARTIAL; over-privilege "confirmed" conclusions are forbidden |
| Complexity/depth limit configuration missing context | Record schema and middleware configuration points | Degrade to Pending Confirmation and list missing items |
| Resolver downstream calls visible but parameter mapping incomplete | Output call sites and candidate variable mappings | Do not output a high-severity exploit chain; defer to follow-up confirmation |
| Introspection exposure visible only in development configuration | Give configuration differences per environment | Conclusion limited to that environment; no generalization |

🔴 **STOP: when the resolver authorization chain and downstream call chain are not closed, outputting a "confirmed exploitable" conclusion is forbidden.**

## Measured Test Cases and Pass Criteria (Mandatory)

- Execute at least 2 typical test cases before each output (happy path + 1 edge/ambiguity scenario), and record expected vs actual differences.
- `full_test >= 1` is required by default; if only `dry_run` is possible, `confidence=LOW` must be marked in the conclusion, with a make-up test plan and owner.
- Pass criteria: key fields complete, evidence chain traceable, conclusion level consistent with gate status; if any fails, marking "passed/deliverable" is forbidden.

## Overall Architecture and Redundancy Control (Mandatory)

- Section organization must keep the three-layer skeleton: `Input Constraints` → `Execution Steps` → `Output and Acceptance`; no layer may be missing or mixed across layers.
- A single paragraph should not exceed 6 lines; synonymous rules must not appear more than twice; duplicated content must be merged into a single source-of-truth section.
- AI-isms and empty filler transitions are forbidden (e.g. "first/second/finally/in summary/put simply/in other words"); any found must be rewritten as executable statements.

## Quality Gate & Assessment Consistency (Mandatory)

- A minimal gate self-check must be executed before producing output: `input completeness`, `key evidence hit`, `output path valid` — all three must be PASS.
- If any of `key evidence missing`, `chain not closed`, `consistency_check_status=BLOCKED` holds, the conclusion must be degraded to `BLOCKED`; outputting "confirmed exploitable/deliverable" is forbidden.
- The report must explicitly record: `gate_status`, `blocked_reasons`, `recheck_action`, and be traceably aligned with the `quality/*` artifacts.

## Do NOT Do (Anti-Pattern Blacklist)

| # | Anti-Pattern | Why Not | Correct Approach |
|---|---|---|---|
| 1 | Lumping Query/Mutation/Subscription into one category | Attack surfaces differ significantly | Draw conclusions per type |
| 2 | Judging introspection-on as directly high-risk | Must be combined with authorization and reachability | Give exposure conditions and exploitation prerequisites |
| 3 | Only looking at the schema, not resolver implementations | Evidence is insufficient and misjudgment is likely | Must drill down into resolver code |
