# Blazor Framework Specialty Audit

## Shared Grabber Index References

- By default, use shared/DOTNET_AUDIT_GRABBER_INDEX.md as this Skill's base retrieval index
- By default, use shared/DOTNET_SINK_REFERENCE.md as this specialty's sink type definition and trace-gate validation baseline
- By default, follow the common execution standard in `skills/shared/DOTNET_AUDIT_EXECUTION_STANDARD.md` (two-phase determination, fail-close determination, testing requirements)
- Enumeration must at least cover Blazor-related entry definitions, binding conversions, pre-controls, sensitive operations, and security configuration grabbers
- If the project has framework secondary encapsulation, unified extension methods, a platform base, or a host wrapper layer, they must be added to the in-project grabbers section of the output
- When this Skill's specialty enumeration rules are more detailed than the shared index, this Skill prevails, but the shared index's base coverage must not be reduced

## Input Dependencies

- Required: `source_path`
- Optional: `route_mapping/routes_{timestamp}.md` and `route_mapping/params_{timestamp}.md` (if already generated by `dotnet-route-mapper`, used to align page/API entry points, parameter bindings, and `route_id`)
- Optional: `auth_audit/auth_mapping_{timestamp}.md` (if component-level authorization, page-level authorization, and backend API authorization boundaries need to be aligned)
- Optional: `route_tracer/{route_id}/trace_{timestamp}.md` and `route_tracer/{route_id}/trace_summary_{timestamp}.md` (if component events, backend API calls, and server-side side-effect chains need to be cross-referenced)

## Key Checks

- Blazor Server event handling, component lifecycle, Circuit reconnection, state synchronization, and server-side side-effect entry points
- Output boundaries of MarkupString, RenderFragment, dynamic components, parameter cascading, template components, and third-party UI components
- JSInterop input/output trust boundaries, browser local storage, clipboard, file access, navigation, and frontend script interop
- Blazor WebAssembly client code exposure, token storage, API call chains, offline cache, and source map leakage
- Whether identity authentication state providers, tenant context, component-level authorization, page-level authorization, and backend API authorization are consistent
- State leakage and double-execution issues when prerendering, static SSR, and interactive rendering are mixed

## Enumeration Rules (Mandatory Refinement)

- Enumerate all .razor components, page routes, event handlers, lifecycle methods, AuthorizeView, CascadingParameter, JSInvokable, and JSRuntime call sites
- Search with priority: @page, @onclick, NavigationManager, MarkupString, RenderFragment, AuthorizeView, AuthenticationStateProvider, IJSRuntime, ProtectedLocalStorage, ProtectedSessionStorage
- Distinguish Blazor Server, Blazor WebAssembly, interactive SSR, and prerendered hybrid modes; record which side the state lives on, which side the token lives on, and whether double execution or state drift exists
- Enumerate file upload, navigation redirects, client-side cache, offline storage, clipboard, and browser API interop; record which inputs enter server-side side effects or output contexts
- For each key component record: route, authorization method, state dependencies, JS interop, backend API calls, and triggerable side-effect types

## Barrier Verification Matrix (Mandatory)

Assess against the fail-close three-tier standard in `DOTNET_AUDIT_EXECUTION_STANDARD.md`:

| Tier | Check Item | Pass Criteria | Failure Degradation |
|------|--------|----------|----------|
| Tier 1 | Component/event entry exists and is user-triggerable | A .razor component route, @onclick event, and JSInvokable callback exist and are actually user-triggerable | BLOCKED → no user-triggerable entry; the specialty is deprioritized |
| Tier 2 | State sync/JSInterop has data leakage or injection | MarkupString/RenderFragment/JSRuntime calls have unencoded output or parameter injection, or state synchronization leaks across Circuits | BLOCKED → state sync and JSInterop boundaries are safe; conclusion degraded |
| Tier 3 | Backend call chain is unauthorized or over-privileged | Backend API/Hub/service calls triggered by components lack business authorization, or Blazor Server/WASM authorization boundaries are inconsistent | PARTIAL → only potential risks and verification steps are output |

## Two-Phase Determination Flow (Mandatory)

- **Phase 1 (Initial Screening Hit)**: component/event entry + state sync/JSInterop + backend call chain hit; output `Hit ID: M{hash}`.
- **Phase 2 (Refined Confirmation)**:
  1. Trace in reverse: component route/event → state sync → JSInterop chain;
  2. Verify the encoding boundaries and parameter controllability of MarkupString/RenderFragment/JSRuntime;
  3. Assess the authorization boundaries of backend API/Hub/service calls and Blazor Server/WASM differences;
  4. If all three barrier tiers pass → `Confirmed Vulnerability`; if any fails → degrade per the matrix.

## Determination Rules and Priority (Mandatory)

1. **Confirmed Vulnerability**: component entry triggerable + state sync/JSInterop has a security issue + backend call unauthorized. Output `Confirmed Vulnerability`.
2. **Pending Confirmation**: component/JSInterop/backend call evidence partially exists, but the authorization chain or state boundary cannot be proven. Output `Pending Confirmation`.
3. **False Positive / No Risk**: component entry is authorized, JSInterop parameter validation is strict, backend call authorization is complete, Server/WASM boundaries are clear. Output `False Positive` with determination basis.

## Testing Suggestions and Minimum Trigger Conditions (Mandatory)

- **Minimum Trigger Conditions**:
  - A Blazor component (.razor) or JSInterop call exists
  - A user-triggerable component route/event/callback exists
  - Or MarkupString/RenderFragment/JSRuntime has unencoded output/parameter injection
  - Or a backend API/Hub call lacks business authorization
- **Test Case Suggestions**:
  - Happy Path: normal component rendering and event handling, state synchronization is safe, JSInterop parameter validation is correct
  - Edge/Ambiguity: Circuit reconnection state drift, prerendering + interactive rendering double execution, ProtectedLocalStorage token leakage, WASM client code exposure
- Each hit output appends `Hit ID: M{hash}` and `test_id: T{hash}` for traceability.

## Checkpoint Design (Mandatory)

- 🔴 **CHECKPOINT A (Entry Inventory Confirmation)**: must confirm component routes, event callbacks, and parameter binding entries are complete.
- 🔴 **CHECKPOINT B (Data Flow Closure Confirmation)**: must confirm the intermediate chain from user input to sensitive operations is traceable.
- 🔴 **CHECKPOINT C (Protection Evidence Confirmation)**: must confirm authorization, encoding, and validation protection evidence can be written to disk.
- 🛑 **STOP**: if entries or evidence chains are not closed, the conclusion is degraded to `⚠️Pending Verification`.

## Executable Parameters and Output Templates (Mandatory)

- Audit conclusion level: `Confirmed` / `⚠️Pending Verification` / `Not Applicable` (choose exactly one; leaving blank is forbidden).
- Minimum evidence set: must include at least the five items `entry point`, `controllable parameters`, `key calls`, `security boundary`, `missing evidence`.
- Output file naming: uniformly use `{topic}_{timestamp}.md`, aligned with `IO_PATH_CONVENTION.md`.
- Softening wording is forbidden: e.g. "possibly at risk / worth noting / depends on the situation / very likely"; when evidence is insufficient, must explicitly write `⚠️Pending Verification` and the next follow-up confirmation action.

Minimal output snippet (directly reusable):

```md
- Audit conclusion level: Confirmed
- Minimum evidence set: entry point=...; controllable parameters=...; key calls=...; security boundary=...; missing evidence=none
- Next action: if gaps exist, supplement parameter propagation evidence for trace_id=...
```

## Failure and Degradation Branches (Mandatory)

| Trigger Condition | First-Line Handling | Fallback if Still Failing |
|---|---|---|
| Component authorization visible but backend API authorization chain incomplete | Output component-level and API-level authorization evidence | Mark PARTIAL; over-privilege "confirmed" conclusions are forbidden |
| JSInterop call site visible but parameter source unclear | Output call site and candidate sources | Degrade to Pending Confirmation and list missing items |
| Server/WASM hybrid mode boundary unclear | Record state and token locations on both sides separately | Split conclusions by mode and degrade |
| Prerendering vs interactive rendering execution difference unprovable | Output lifecycle evidence and assumptions | Mark Environment-Dependent; no strong conclusion |

🔴 **STOP: when the component state chain and backend call chain are not closed, outputting a "confirmed exploitable" conclusion is forbidden.**

## Measured Test Cases and Pass Criteria (Mandatory)

- Execute at least 2 typical test cases before each output (happy path + 1 edge/ambiguity scenario), and record expected vs actual differences.
- `full_test >= 1` is required by default; if only `dry_run` is possible, `confidence=LOW` must be marked in the conclusion, with a make-up test plan and owner.
- Pass criteria: key fields complete, evidence chain traceable, conclusion level consistent with gate status; if any fails, marking "passed/deliverable" is forbidden.

## Overall Architecture and Redundancy Control (Mandatory)

- Section organization must keep the three-layer skeleton: `Input Constraints` → `Execution Steps` → `Output and Acceptance`; no layer may be missing or mixed across layers.
- A single paragraph should not exceed 6 lines; synonymous rules must not appear more than twice; duplicated content must be merged into a single source-of-truth section.
- AI-isms and empty filler transitions are forbidden (e.g. "first/second/finally/in summary/put simply/in other words"); any found must be rewritten as executable statements.

## Quality Gate & Assessment Consistency (Mandatory)

- A minimal gate self-check must be executed before producing output: `input completeness`, `key evidence hit`, `output path valid` — all three must be PASS.
- If any of `key evidence missing`, `chain not closed`, `consistency_check_status=BLOCKED` holds, the conclusion must be degraded to `BLOCKED`; outputting "confirmed exploitable/deliverable" is forbidden.
- The report must explicitly record: `gate_status`, `blocked_reasons`, `recheck_action`, and be traceably aligned with the `quality/*` artifacts.

## Do NOT Do (Anti-Pattern Blacklist)

| # | Anti-Pattern | Why Not | Correct Approach |
|---|---|---|---|
| 1 | Mixing Blazor Server and WASM risks together | Threat models differ | Conclusions must be output per side |
| 2 | Only looking at frontend components, ignoring backend side effects | Actual impact cannot be determined | Correlate backend API/service call chains |
| 3 | Ignoring JSInterop parameter controllability | DOM/command chain risks are easily missed | Parameter sources and destinations must be recorded |

Output type mapping: XSS, AUTH, LOGIC, CFG, SESS.
