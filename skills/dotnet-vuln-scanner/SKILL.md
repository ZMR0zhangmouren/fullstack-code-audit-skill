# NuGet Supply Chain Vulnerability Scan

## Objective

Identify known vulnerabilities in project dependencies, and align component vulnerabilities with potentially affected entry points or functional domains.

## Inputs

- `source_path`
- Optional: `route_mapping/routes_{timestamp}.md` and `route_mapping/params_{timestamp}.md` (if already generated by `dotnet-route-mapper`, used to map affected components to unified entry points and `route_id`)
- Optional: `auth_audit/auth_mapping_{timestamp}.md` (if affected components need to be ranked together with anonymous/P0/P1 entry points)
- Optional: `offline_audit_report` (user-injected offline scan report — output of `dotnet list package --vulnerable`; when provided, parse (package, version, vulnerability ID, severity) and join with the local dependency manifest into the conclusions; list "Hits from injected report" and "Hits from built-in knowledge" as two separate groups in the artifact)

## Mandatory Actions

- Parse dependency package names and versions
- Identify affected version ranges
- Output the locations in code that directly reference the component
- Infer the possibly affected route_id or entry point type

## Failure and Degradation Branches (Mandatory)

| Trigger Condition | First-Line Handling | Fallback if Still Failing |
|---|---|---|
| Dependency files missing (`*.csproj`/`Directory.Packages.props`/`packages.config`) | Continue scanning the remaining dependency manifest files and record the missing manifests | Output `⚠️Incomplete dependency manifest`, conclusion degraded to PARTIAL |
| Version range cannot be parsed (floating versions, conditional references) | Record the raw version expression and attempt normalized parsing | Mark with `Pending Verification` and enter the risk pool; do not output "Confirmed affected" |
| Vulnerability database has no match or version mapping is inconsistent | Record the component and version and keep the "no confirmed evidence" note | Output `Environment-Dependent/Needs external intelligence for confirmation`; writing "no risk" is forbidden |
| Package has no direct reference in code | First mark it as a transitive dependency and continue analyzing the dependency chain | If the chain cannot be closed, mark it `SINK_SUSPECT`, pending cross-confirmation by route-tracer/framework |

🔴 **STOP: when any fallback branch is triggered, outputting a "completely risk-free" conclusion is forbidden.**

## Resource References & Reachability Validation (Mandatory)

- Required shared index references: `skills/shared/DOTNET_AUDIT_GRABBER_INDEX.md` (grabber sources) and `skills/shared/EVIDENCE_POINT_IDS.md` (evidence criteria).
- Output criteria validation: on-disk paths and naming must align with `skills/shared/IO_PATH_CONVENTION.md`; custom deviations from the directory structure are not allowed.
- Evidence consistency validation: if severity-graded conclusions are cited, they must be consistent with `skills/shared/SEVERITY_RATING.md`.
- Reachability check: before submission, confirm at least once that key referenced files are accessible (e.g. `DOTNET_AUDIT_GRABBER_INDEX.md`, `IO_PATH_CONVENTION.md`).

## Measured Test Cases and Pass Criteria (Mandatory)

- Each skill must maintain at least 2 typical test cases (happy path + one complex scenario), and annotate the case ID in the results.
- Each evaluation round must execute `full_test` for at least 1 case; if only `dry_run` is possible, `dry_run_reason` and a make-up test plan must be recorded.
- Pass criteria must simultaneously satisfy: `intent achieved`, `key evidence hit`, `output format compliant`; if any one is not met, "pass" must not be given.

## Overall Architecture and Redundancy Control (Mandatory)

- Section organization must keep the three-layer skeleton: `Input Constraints` → `Execution Steps` → `Output and Acceptance`; no layer may be missing or mixed across layers.
- A single paragraph should not exceed 6 lines; synonymous rules must not appear more than twice; duplicated content must be merged into a single source-of-truth section.
- AI-isms and empty filler transitions are forbidden (e.g. "first/second/finally/in summary/put simply/in other words"); any found must be rewritten as executable statements.

## Quality Gate & Assessment Consistency (Mandatory)

- A minimal gate self-check must be executed before producing output: `input completeness`, `key evidence hit`, `output path valid` — all three must be PASS.
- If any of `key evidence missing`, `chain not closed`, `consistency_check_status=BLOCKED` holds, the conclusion must be degraded to `BLOCKED`; outputting "confirmed exploitable/deliverable" is forbidden.
- The report must explicitly record: `gate_status`, `blocked_reasons`, `recheck_action`, and be traceably aligned with the `quality/*` artifacts.

## Do NOT Do (Anti-Pattern Blacklist)

| # | Anti-Pattern | Why Not | Correct Approach |
|---|---|---|---|
| 1 | Judging safe just because "no vulnerability database hit" | Missing intelligence does not equal no risk | Explicitly mark "no confirmed evidence" and keep a path for follow-up confirmation |
| 2 | Ignoring transitive dependencies | Second-level dependencies are often the real attack surface | At least record transitive dependencies and affected paths |
| 3 | Reporting only the package name without version ranges | Cannot be used for remediation or reproduction | Must give affected versions and the current version |
| 4 | Not aligning with route_id/functional domain | Cannot enter pipeline risk ranking | Output affected entry point or module mapping |

## Workflow (Input → Execution → Output)

1. Input: read `source_path` and upstream artifacts (e.g. `route_mapping` / `route_tracer` / `framework_audit`), confirm dependencies are available and timestamps are consistent.
2. Execution: complete the audit in the order "shared grabber index → this specialty's enumeration rules → evidence point references", recording hit points, evidence chains, and unclosed paths.
3. Output: write to the agreed path per the "Output" section of this file; conclusions must be annotated `Confirmed` / `⚠️Pending Verification`, with a missing-evidence list attached.

## Checkpoint Design (Mandatory)

- 🔴 **CHECKPOINT A (Asset Inventory Confirmation)**: must confirm the NuGet dependency, version, and source manifest is complete.
- 🔴 **CHECKPOINT B (Vulnerability Match Confirmation)**: must confirm the CVE/GHSA match rules and evidence sources.
- 🔴 **CHECKPOINT C (Remediation Suggestion Confirmation)**: must confirm the remediation versions and compatibility impact are actionable.
- 🛑 **STOP**: if the vulnerability match basis is incomplete, outputting a "no high risk" conclusion is forbidden.

## Executable Parameters and Output Templates (Mandatory)

- Audit conclusion level: `Confirmed` / `⚠️Pending Verification` / `Not Applicable` (choose exactly one; leaving blank is forbidden).
- Minimum evidence set: must include at least the five items `entry point`, `controllable parameters`, `key calls`, `security boundary`, `missing evidence`.
- Output file naming: uniformly use `{topic}_{timestamp}.md`, aligned with `IO_PATH_CONVENTION.md`.
- Softening wording is forbidden: e.g. "possibly at risk / worth noting / depends on the situation / very likely"; when evidence is insufficient, must explicitly write `⚠️Pending Verification` and the next follow-up confirmation action.

Minimal output snippet (directly reusable):

```md
- Audit conclusion level: Confirmed
- Minimum evidence set: entry point=...; controllable parameters=...; key calls=...; security boundary=...; missing evidence=none
- Next action: if gaps exist, supplement parameter propagation evidence for trace_id=...
```

## Output

- vuln_report/{project_name}_nuget_vuln_report_{timestamp}.md
- The artifact header must contain `knowledge_cutoff_date: {YYYY-MM-DD|unknown}` (built-in knowledge declaration cutoff date; when unknown, accompanied by a "conclusions may be outdated" statement) and `offline_report_source: {path|none}`; when there is no injected report and no online comparison, a "no online comparison performed" statement is mandatory.
- **Field-level compliance matrix (2026-09-20, mandatory)**: `knowledge_cutoff_date` / `offline_report_source` are **literal fields** that must be present verbatim — an exact string match is required for compliance; semantically equivalent rewrites (e.g. "knowledge cutoff date", "offline report source", "data timeliness statement") are treated as non-compliant and handled as missing fields.
