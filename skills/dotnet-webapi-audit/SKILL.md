## Key Checks

- API authentication, anonymous routes, versioned routes, route constraints, OpenAPI grouping, and gateway/reverse-proxy prefix mapping

## Enumeration Rules (Mandatory Refinement)

- Enumerate all ApiControllers, Minimal APIs, versioned routes, RoutePrefix/MapGroup, custom constraints, and gateway prefix mappings; record externally reachable paths and version differences
- Search with priority: ApiController, ProducesResponseType, FromBody, FromQuery, FromRoute, FromHeader, JsonPatchDocument, ProblemDetails, EnableCors, AddSwaggerGen, AddEndpointsApiExplorer
- Enumerate input DTOs, Patch models, batch endpoints, webhooks, callback addresses, file upload, and streaming download entries; record field sources, batch write capability, and authentication methods
- Enumerate serialization configuration: System.Text.Json, Newtonsoft.Json, ReferenceHandler, TypeNameHandling, custom JsonConverters, polymorphic resolution, and error formatting logic
- For each API record: route template, authentication method, binding source, serializer, error output, documentation exposure surface, and whether it faces internal or external callers
- **Dimension bar (mandatory, 2026-09-20): signature replay** — check the signature middleware registration order and reachability (whether it runs after authentication/rate limiting, and whether it can be short-circuited globally or bypassed by a branch pipeline), the exposure surface of signature entry routes, and item by item the effectiveness of the nonce/timestamp/replay cache trio in the request processing pipeline (request-processing-surface determination see the "Mechanism Extension: Signed Request Replay Protection" section of this file; signature/verification implementation surface see the same-named dimension bar in `dotnet-crypto-audit` — the two files cross-reference each other and share one determination standard). Not-applicable determination condition: the target has no API key + signature/HMAC/webhook signature verification middleware or entry at all, and an rg negative-evidence citation (scope + pattern, e.g. `rg "UseHmac|SignatureVerification|VerifySignature" {scope}` with zero hits) is attached before marking `Not Applicable`; otherwise a bare "not covered" is forbidden

## Barrier Verification Matrix (Mandatory)

Assess against the fail-close three-tier standard in `DOTNET_AUDIT_EXECUTION_STANDARD.md`:

| Tier | Check Item | Pass Criteria | Failure Degradation |
|------|--------|----------|----------|
| Tier 1 | API endpoint exposed and version/route reachable | An externally reachable API endpoint exists (including versioned routes/gateway prefixes) and is accessible anonymously or with weak authentication | BLOCKED → all APIs are strongly authenticated and unreachable; the specialty is deprioritized |
| Tier 2 | Binding/serialization has a bypass or sensitive information exposure | DTO/Patch/batch endpoints have over-posting, or serialization configuration (TypeNameHandling/ReferenceHandler) causes type confusion/information leakage | BLOCKED → binding and serialization chains are complete with no bypass; conclusion degraded |
| Tier 3 | Incomplete authentication/authorization chain causes over-privilege | API authentication missing, JWT validation parameters loose, CORS configuration overly permissive, or internal API boundary unclear | PARTIAL → only potential risks and verification steps are output |

## Two-Phase Determination Flow (Mandatory)

- **Phase 1 (Initial Screening Hit)**: API entry + binding/serialization configuration + authentication/authorization chain hit; output `Hit ID: M{hash}`.
- **Phase 2 (Refined Confirmation)**:
  1. Trace in reverse: API route → version/gateway prefix → authentication method chain;
  2. Verify over-posting in DTO/Patch/batch endpoints and serialization configuration (TypeNameHandling/ReferenceHandler) risks;
  3. Assess whether JWT/CORS/documentation exposure causes over-privilege or information leakage;
  4. If all three barrier tiers pass → `Confirmed Vulnerability`; if any fails → degrade per the matrix.

## Determination Rules and Priority (Mandatory)

1. **Confirmed Vulnerability**: API externally reachable + binding/serialization bypass + incomplete authentication/authorization chain. Output `Confirmed Vulnerability`.
2. **Pending Confirmation**: API/binding/authentication evidence partially exists, but the deployment environment or runtime behavior cannot be proven. Output `Pending Confirmation`.
3. **False Positive / No Risk**: all APIs are strongly authenticated, binding chain is complete, serialization configuration is safe, CORS is strict. Output `False Positive` with determination basis.

## Testing Suggestions and Minimum Trigger Conditions (Mandatory)

## Mechanism Extension: Signed Request Replay Protection (2026-09-14 Ledger Round)

### Mechanism Description and Boundary

Untrusted signed request → freshness check missing (nonce/timestamp/replay cache) → replay succeeds. After capturing one legitimate signed request, the attacker resubmits it verbatim or with minor modifications; if the server only verifies the signature without checking freshness, the replayed request is processed as legitimate, causing repeated state changes such as duplicate charges or duplicate orders.

This Skill (dotnet-webapi-audit) focuses on the **request-processing surface**: the signature middleware registration order and reachability (whether it runs after authentication/rate limiting, whether it can be short-circuited globally), and the exposure surface of signature entry routes. The signature/verification implementation itself is covered by the same-named extension in dotnet-crypto-audit; both share one determination standard.

Ledger boundary (verbatim): a valid signature ≠ a fresh request; must not be merged with HTTP query construction; signature algorithm or key management issues are out of scope for this extension.

### Key Checks and Enumeration Grabbers

Record for each hit: file, line number, middleware/route, and the missing freshness component.

- **Signature verification entry**: custom middleware for API key + signature, registration position and scope of `UseHmacSignature` / custom verification middleware / `SignatureVerification` helper methods.
- **Freshness trio existence**:
  - Nonce storage and uniqueness validation: writes and lookups of nonce records in `IDistributedCache` / `MemoryCache`, and whether storage is shared under distributed deployment (single-node `MemoryCache` fails under multiple instances).
  - Timestamp window and skew tolerance: existence of timestamp deviation validation in the request processing pipeline and the skew limit.
  - Replay cache expiration policy: expiration policy of nonce/timestamp records, and whether duplicate submissions before expiration are rejected.
- **Signature coverage**: whether the signed string covers method, path, timestamp, nonce, and body; whether signature verification fails when a route rewrite/gateway rewrites the path.
- **Middleware order and reachability**: whether the verification middleware takes effect before endpoint execution, whether an earlier middleware short-circuits (e.g. global exception handling swallowing verification failures), and whether MapGroup / branch pipelines bypass verification.

### Verification Matrix

| Barrier Type | Verification Action | Determination Criteria |
|-------------|---------|---------|
| **Nonce uniqueness enforcement** | Confirm that a used nonce is rejected in the request processing pipeline; whether nonce storage is shared under multi-instance deployment | Reject-on-use and cross-instance sharing → ✅ Safe; single-node cache with multiple instances, or duplicate nonces accepted → 🔴 High-risk Pending Confirmation |
| **Timestamp window validation** | Confirm timestamp deviation validation is effective in the pipeline and out-of-window requests are rejected | Fail-close window validation → ✅ Safe; no window validation or unlimited tolerance → 🔴 High-risk Pending Confirmation |
| **Replay cache not bypassable** | Confirm cache miss (nonce absent) rejects by default; confirm no middleware short-circuit or branch pipeline bypasses verification | Miss-rejects-by-default and not bypassable → ✅ Safe; miss-passes-by-default or bypassable → 🔴 High-risk Pending Confirmation |
| **Signature coverage completeness** | Verify method+path+timestamp+nonce+body full coverage, including mismatch handling after gateway/proxy path rewrites | Full coverage → ✅ Safe; timestamp/nonce not covered by the signature → 🔴 High-risk Pending Confirmation |

🔴 **STOP: when any barrier verifies as `silent-fallback` or `fail-open`, marking the conclusion "Confirmed Safe" or "False Positive" is forbidden.**

### Determination Rules

Confirmation requires simultaneously closing the following three EVIDs; none may be missing:

1. **Freshness absence closure**: evidence that the signature verification entry lacks nonce/timestamp/replay cache freshness validation (`EVID_CRYPTO_REPLAY_FRESHNESS_ABSENT`).
2. **Replay acceptance closure**: empirical evidence that the same signed request is accepted on a second submission (`EVID_CRYPTO_REPLAY_ACCEPTANCE`).
3. **Impact closure**: impact closure evidence that replay causes over-privileged operations/state changes (`EVID_CRYPTO_REPLAY_IMPACT_CONFIRM`).

🔴 **Confirmation threshold (ledger verbatim): must prove freshness validation is absent AND the replayed request is accepted.** webapi focuses on the request-processing surface (middleware order, signature entry reachability); crypto focuses on the signature/verification surface; both share one determination standard.

### Testing Suggestions

- **Positive**: capture a signed request through the real pipeline and replay it verbatim, confirming it is accepted; modify the timestamp and replay through the pipeline, confirming it still passes.
- **Negative**: when nonce uniqueness + window validation are complete, confirm a replayed request is rejected at the middleware layer.
- **Regression**: when adding a signed endpoint or adjusting middleware order, re-verify the freshness trio and the reachability of the verification middleware.

### Evidence References

- `EVID_CRYPTO_REPLAY_FRESHNESS_ABSENT`: evidence that the signature verification entry lacks nonce/timestamp/replay cache freshness validation
- `EVID_CRYPTO_REPLAY_ACCEPTANCE`: empirical evidence that the same signed request is accepted on a second submission
- `EVID_CRYPTO_REPLAY_IMPACT_CONFIRM`: impact closure evidence that replay causes over-privileged operations/state changes
