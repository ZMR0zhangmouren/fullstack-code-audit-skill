## Key Checks

- Priority and coverage relationships among [Authorize], AllowAnonymous, Policy, Role, Claim, AuthenticationSchemes, and global filters
- Parsing and validation flows of JWT, Cookie, Session, Identity, Windows/Auth, OpenID Connect, API Key, and custom signed tickets
- TokenValidationParameters, signature algorithms, key rotation, issuer/audience/clock skew, ticket persistence, and sliding expiration configuration
- Resource ownership validation, tenant isolation, consistency between organizationId/tenantId/userId and route/body parameters, identifying IDOR and over-privilege
- Custom authorization chains and missing points of different entries such as Controllers, Minimal APIs, Hubs, GraphQL Resolvers, Background APIs, and WCF Services
- External identity source mapping, local role caching, claim transformation, impersonation, sudo/admin switch, and backdoor role logic
- Whether login, logout, password reset, second-factor verification, remember me, device trust, and exception fallback branches create bypass surfaces

## Enumeration Rules (Mandatory Refinement)

- If `design_intent` artifacts exist, first check the "permission and tenant boundary intent" against actual authorization definitions (deviations are registered as documentation-implementation drift and are not directly escalated to vulnerability conclusions)
- Enumerate all [Authorize], AllowAnonymous, Policy, Roles, AuthenticationSchemes, RequireAuthorization, and MapGroup-level authorization definitions
- Search with priority: AddAuthentication, AddAuthorization, TokenValidationParameters, CookieAuthenticationOptions, IdentityOptions, IAuthorizationHandler
- Enumerate authentication/authorization entries of Controllers, Minimal APIs, Hubs, GraphQL Resolvers, WCF Services, admin APIs, and internal APIs
- Enumerate identity flow endpoints such as login, logout, registration, password reset, 2FA, external login, device trust, tenant switching, and admin impersonation
- For each authorization point record: entry type, authentication scheme, permission judgment source, resource ownership fields, exception/fallback branches, default-allow paths
- **Dimension bar (mandatory, 2026-09-20): error response consistency** — endpoint-by-endpoint consistency check of error responses for authentication endpoints such as login, password recovery, registration, and 2FA: conclusions are required for all three difference surfaces of status codes, error messages, and timing-distinguishable signals (enumeration surface, verification matrix, and determination threshold see the "Mechanism Extension: Account Enumeration" section of this file). Not-applicable determination condition: the target has no authentication/registration/recovery endpoints at all, and an rg negative-evidence citation (scope + pattern, e.g. `rg "SignIn|PasswordSignIn|FindByEmail" {scope}` with zero hits) is attached before marking `Not Applicable`; otherwise a bare "not covered" is forbidden

## Barrier Verification Matrix (Mandatory)

This specialty must perform verification on the following barrier types, assessed against the fail-close standard in `DOTNET_AUDIT_EXECUTION_STANDARD.md`:

| Barrier Type | Verification Action | Determination Criteria |
|-------------|---------|---------|
| **Authentication scheme execution** | Confirm that after the `[Authorize]`/`RequireAuthorization` annotation, the authentication middleware actually executes (not just annotated) | Actually executes and rejects on failure → ✅ Safe; annotation exists but middleware not registered / skipped → 🔴 High-risk |
| **Authorization policy resolution** | Read Policy/Role/Claim validation source code, confirming whether it is fail-close (no matching policy → reject) | Fail-close (reject on no match) → ✅ Safe; fail-open (allow by default on no match) → ⚠️ Bypassable; no policy validation → 🔴 High-risk |
| **Resource ownership validation (IDOR)** | Confirm whether resource operations validate the current user/tenant's ownership of the target resource beforehand | Strict resource ownership validation → ✅ Safe; identity validation only without ownership → ⚠️ Pending Confirmation; no validation → 🔴 High-risk |
| **Anonymous exceptions and fallback branches** | Check AllowAnonymous coverage entry by entry, confirming whether fallback branches (e.g. default behavior after authentication failure) allow by default | No unexpected anonymous entries, fallback branches reject → ✅ Safe; unrecorded anonymous entries exist or fallback branches allow → 🔴 High-risk |
| **Token validation completeness** | Confirm whether JWT/Token validation is complete: signature verification, issuer, audience, expiration, clock skew | All validations performed and keys secure → ✅ Safe; signature verification skipped or parse-only → 🔴 High-risk; partial validation → ⚠️ Pending Confirmation |
| **Privilege escalation and privileged switching** | Confirm whether impersonation, sudo/admin switch, backdoor roles, or other privileged switching logic exists | No privileged switching, or strict secondary validation → ✅ Safe; an exploitable privileged switching path exists → 🔴 High-risk |

🔴 **STOP: when any barrier verifies as `silent-fallback` or `fail-open`, marking the conclusion "Confirmed Safe" or "False Positive" is forbidden.**

## Two-Phase Determination (Mandatory)

Follow the two-phase determination flow in `DOTNET_AUDIT_EXECUTION_STANDARD.md`:

1. **Phase 1 (Interim Conclusion)**: for each hit, first mark `Confirmed Vulnerability Candidate` / `Pending Confirmation` / `False Positive`
2. **Phase 2 (Mandatory Evidence Chasing)**:
   - If Phase 1 is `Confirmed Vulnerability Candidate` → all relevant items of the Barrier Verification Matrix must be completed and passed before marking `Confirmed`
   - If Phase 1 is `Pending Confirmation` → at least one more hop of the call chain or downstream parser must be traced until a determination is possible
   - If Phase 2 still cannot close the case → keep `Pending Confirmation`, and explicitly record which hop of evidence is missing

## Determination Rules (Mandatory Refinement)

### Confirmed Vulnerability

At least one of the following conditions holds:

1. The authentication middleware is not registered or is skipped; the `[Authorize]` annotation exists but does not actually execute
2. The authorization policy is `fail-open` (allows by default on no match), or missing resource ownership validation causes IDOR
3. AllowAnonymous coverage is too broad, or unrecorded anonymous entries exist that bypass authentication
4. JWT/Token validation skips signature verification, or parses claims only without validating legitimacy
5. An exploitable privileged switching path exists (e.g. a regular user can switch to the admin role via a parameter)
6. In nested/recursive structures (e.g. multi-layer PolicyResolver encapsulation), the top layer has validation but sub-layers perform no equivalent validation

### Pending Confirmation

1. The context shows a suspicious pattern (e.g. an `[Authorize]` annotation), but middleware registration and execution order cannot be confirmed
2. A barrier function (e.g. resource ownership validation) exists, but whether the current branch invokes it and whether its return value is used cannot be confirmed
3. Permission context propagation in asynchronous/queue/event chains (e.g. message queue triggering background tasks) is not closed
4. Token validation parameters (e.g. `TokenValidationParameters`) are scattered across multiple places, making complete validation behavior unconfirmable

### False Positive

1. An entry has an explicit `AllowAnonymous` and the business is designed that way (e.g. a public API); not a vulnerability
2. All recursion levels reuse the same fail-close authorization policy validator
3. Resource ownership validation is strict and not bypassable; the current user can only access resources they own
4. Token validation is complete (signature + issuer + audience + expiration) with secure key management

## Testing Suggestions (Mandatory)

Follow the testing requirements in `DOTNET_AUDIT_EXECUTION_STANDARD.md`; for each confirmed vulnerability or pending-verification item provide:

- **Positive test**: construct an over-privileged request (e.g. modify the `userId` parameter to access others' resources, remove the token signature portion, switch the role parameter) to verify the vulnerability actually exists
- **Negative test**: construct input intercepted by a barrier (e.g. an invalid token, a JWT with an unauthorized role, a cross-tenant resource ID) to verify the protection is effective
- **Regression test**: retest after remediation, confirming the barrier still works and no new bypass path is introduced (e.g. fallback branches allowing by default, new anonymous entries)

Test cases must be annotated with `test_id` and linked to the corresponding hit ID in the audit report.

## Mechanism Extension: Account Enumeration (2026-09-14 Ledger Round)

### Mechanism Description and Boundary

Untrusted login request → authentication error response → account existence / authentication state / error type distinguishable signals. By comparing the differences in status codes, response bodies, and timing across the three paths of success, failure, and nonexistent account, the attacker infers states such as whether an account exists, whether it is locked, and which authentication method is used.

Ledger boundary (verbatim: incorporated into the existing authentication audit error-response-consistency dimension; no new enumeration Skill is created; out of scope for this extension: authentication bypass / password brute force, which belong to the existing authentication dimension).

### Key Checks and Enumeration Grabbers

Cover at least the following four enumeration surfaces; record for each hit: file, line number, endpoint, and difference signal type (status code / response body / timing):

- **Login endpoint error response branches**: whether ASP.NET Identity `SignInManager.CheckPasswordSignInAsync` / `PasswordSignInAsync` result branches return different responses by `Succeeded` / `IsLockedOut` / `IsNotAllowed` / `RequiresTwoFactor`; whether differences among `ChallengeResult` / `ForbidResult` / `BadRequest` leak account states.
- **Password recovery flow response differences**: whether the responses of the two paths — `UserManager.FindByEmailAsync` returning null vs sending a reset email — are consistent; whether hints like "this email is not registered" directly expose existence.
- **Registration flow existence hints**: whether username/email uniqueness validation returns distinguishable hints such as "this username is already taken", and whether the hint granularity reaches specific field values.
- **Missing response unification middleware**: whether there is no `StatusCodePages` / unified error filter, or a custom exception filter returns different structures on different branches, causing difference leakage; whether a nonexistent account returns early (skipping one hash verification) on timing, forming an observable time difference.

### Verification Matrix

| Barrier Type | Verification Action | Determination Criteria |
|-------------|---------|---------|
| **Response consistency unification** | Submit correct password + existing account / wrong password + existing account / arbitrary password + nonexistent account respectively, and compare the status code and response body fingerprints of the three responses | All three paths have identical fingerprints → ✅ Safe; any distinguishable difference → 🔴 High-risk Pending Confirmation |
| **Timing equalization** | Measure the response time distribution for existing and nonexistent accounts, confirming whether nonexistent accounts go through the same-cost path (hash verification not short-circuited) | Constant timing or unified cost → ✅ Safe; nonexistent accounts noticeably faster → ⚠️ Pending Confirmation |
| **Error message generalization** | Check whether error messages and error codes distinguish "user does not exist" / "wrong password" / "account locked" | Unified generic wording (e.g. "incorrect username or password") with no status code distinction → ✅ Safe; wording or code values distinguishable → 🔴 High-risk Pending Confirmation |

🔴 **STOP: when any barrier verifies as `silent-fallback` or `fail-open`, marking the conclusion "Confirmed Safe" or "False Positive" is forbidden.**

### Determination Rules

Confirmation requires simultaneously closing the following three EVIDs; none may be missing:

1. **Endpoint surface closure**: evidence of login/recovery/registration enumeration surfaces (`EVID_AUTH_ENUM_ENDPOINT_SURFACE`).
2. **Observable difference closure**: evidence of observable differences (at least one of status code / response body / timing) among success / failure / nonexistent accounts (`EVID_AUTH_ENUM_OBSERVABLE_DIFF`).
3. **Impact closure**: impact closure evidence that account existence or authentication state can be inferred (`EVID_AUTH_ENUM_IMPACT_CONFIRM`).

🔴 **Confirmation threshold (ledger verbatim): theoretical differences alone must not be confirmed — observable differences (at least one of response body / status code / timing) must be proven.**

Unified responses with timing equalization → False Positive.

### Testing Suggestions

- **Positive**: send one login request each with a nonexistent account and a wrong password, confirming the response difference (at least one of status code / response body / timing) is observable.
- **Negative**: after unified responses + timing equalization, the two paths are indistinguishable.
- **Regression**: when adding authentication endpoints (including password recovery, registration, 2FA verification), re-verify response consistency.

### Evidence References

- `EVID_AUTH_ENUM_ENDPOINT_SURFACE`: evidence of login/recovery/registration endpoint enumeration surfaces
- `EVID_AUTH_ENUM_OBSERVABLE_DIFF`: evidence of observable differences (at least one of status code / response body / timing) among success / failure / nonexistent accounts
- `EVID_AUTH_ENUM_IMPACT_CONFIRM`: impact closure evidence that account existence or authentication state can be inferred
