# .NET Route & Endpoint Mapper

## Objective

Analyze .NET web project source code and extract the **complete** HTTP route entries and request parameter structures, generating Burp/Repeater-style request templates for security testing, automatically saved as Markdown.

## CRITICAL: Complete Output (Mandatory)

This Skill must output all discovered entries and endpoints; omission is not allowed:

- Omission placeholders are forbidden; complete routes, parameters, and request templates must be output
- Outputting only "key endpoints" or "high-risk endpoints" is forbidden
- Each entry must include: entry type, HTTP method or operation name, path rule, handler location, parameter structure, and a complete request or invocation template
- For Controller scenarios, Controller-level and Action-level routes, versions, Areas, binding sources, and return type differences must be fully expanded

## Core Inputs

Provided by the user:

- `source_path`: .NET project, solution, or repository root

Optional:

- `context_path`: if a reverse proxy, gateway prefix, PathBase, or service prefix exists, it can be used to assemble the complete external path, but a configuration or code evidence source is required
- `codegraph_index_status_{timestamp}.md`: if an index status file exists under the `codegraph/` directory, CodeGraph tools can be used preferentially to accelerate Controller/Action enumeration and route identification

(Single source of truth: this section prevails; differences from pipeline input parameter pass-through see IO_PATH_CONVENTION.md)

## CodeGraph Acceleration Branch (Optional)

If `codegraph/codegraph_index_status_{timestamp}.md` exists and `codegraph_status = AVAILABLE`:

1. Prefer obtaining the Controller/Action/route mapping via `codegraph explore "ASP.NET controllers and routes in {source_path}"`
2. Supplement the action method list and signatures via `codegraph query --kind method`
3. Read Controller source code and Attribute route declarations via `codegraph node {controller_symbol}`
4. Cross-validate the route symbols returned by CodeGraph with manual static analysis results:
   - Consistent items: adopt directly, reducing repeated Read/Grep
   - Different items: mark `⚠️Needs manual review`, with manual analysis prevailing
   - CodeGraph-only items (e.g. routes generated by Source Generators): record the source and include them in the output
5. Scenarios CodeGraph cannot recognize (e.g. dynamic routes, convention-based routes registered in `Program.cs`): still go through manual analysis

If `codegraph_status != AVAILABLE` or the index status file does not exist: fall back completely to the existing static analysis flow without errors or blocking.

**Constraint**: CodeGraph acceleration does not change the output format or field requirements of routes/params; it only changes how information is obtained.

## Coverage Scope (Mandatory)

1. ASP.NET Core / MVC / Web API Controller routes (mandatory)
	- [Route], [HttpGet], [HttpPost], [HttpPut], [HttpDelete], [HttpPatch], [HttpHead], [HttpOptions]
	- [AcceptVerbs] multi-method routes
	- Combinations of Controller-level [Route] with Action-level [Route]/[Http*]
	- Conventional Routing: MapControllerRoute, MapDefaultControllerRoute, Area routes, legacy route templates
	- Match priority and final path composition when Attribute Routing and Conventional Routing coexist
	- API Versioning: URL segment, query, header, and media type version passing
	- Area: AreaAttribute, MapAreaControllerRoute, module prefixes, and admin backend routes
	- Differences between ControllerBase and Controller: view/page-type Controllers vs pure API Controllers must be distinguished
2. ASP.NET Core Minimal API
	- MapGet/MapPost/MapPut/MapDelete/MapPatch/MapMethods
	- MapGroup, MapFallback, RouteGroupBuilder prefixes and filters
3. SignalR Hub
	- Hub methods, server-side entries triggered by OnConnectedAsync/OnDisconnectedAsync
4. GraphQL
	- Public entries and operation names of Query / Mutation / Subscription
5. WCF
	- ServiceContract / OperationContract

## Controller Scenario Enumeration Rules (Mandatory Refinement)

For each Controller / Action, the following information must be explicitly identified:

1. Route declaration source
	- Controller-level attributes
	- Action-level attributes
	- Conventional routes in Program.cs / Startup.cs
	- Area / versioning / gateway prefix / PathBase
2. Final path composition rules
	- Controller template + Action template + Area + version prefix + route constraints
3. HTTP method
	- From explicit declarations such as [HttpGet]/[HttpPost]/[AcceptVerbs]
	- If it is a conventional route without explicit constraints, mark the method constraint as uncertain or inferred from the action name convention
4. Handler type
	- Controller / ControllerBase
	- MVC page controller / API controller / admin backend controller
5. Return type differences
	- IActionResult, ActionResult<T>, JsonResult, FileResult, RedirectResult, ViewResult, ContentResult
	- These return types affect subsequent output template, file download, redirect, JSON response, and page rendering judgments

## Parameter Structure Parsing (Mandatory)

Output the following parameter source and type information for each entry:

1. Path parameters
	- From route template placeholders such as {id}, {slug}, {version:apiVersion}
	- Parameter name, constraints, nullability, and default values must be output
2. Query parameters
	- [FromQuery], default simple type binding, pagination/sort/filter parameters
3. Body parameters
	- [FromBody], JSON / XML / protobuf / custom input formatters
	- Complex objects must have their field structures expanded, not just the DTO type name
4. Form parameters
	- [FromForm], form fields, multipart form fields
5. Header parameters
	- [FromHeader], authentication headers, version headers, signature headers, tenant headers, custom context headers
6. Service parameters
	- [FromServices] is not user-controllable input, but must be marked as service injection to avoid confusion with user input
7. File parameters
	- IFormFile, IFormFileCollection, file lists, streaming upload objects
8. Custom binding
	- Custom ModelBinders, TypeConverters, BindAsync, TryParse, custom input formatters
	- If parameters are bound by these mechanisms, the binder source and conversion rules must be recorded

## Controller Details Requiring Special Identification (Mandatory)

1. Model Binding rules
	- [ApiController] automatic 400, default binding sources for complex objects, default query/route binding for simple types
	- BindRequired, BindNever, ValidateNever, BindProperty, TryUpdateModel
2. Upload parameters
	- IFormFile / IFormFileCollection / List<IFormFile> / file properties in nested DTOs
3. Versioning
	- [ApiVersion], MapToApiVersion, URL segment, query/header/media type version sources
4. Areas and backend entries
	- [Area], admin/manage/backoffice module paths
5. Custom action selection
	- ActionName, NonAction, RemoteService, actions generated by custom conventions or framework encapsulation
6. Output template differences
	- FileResult: a download-type template is required
	- RedirectResult: a redirect-type template is required
	- JsonResult / ActionResult<T>: a JSON-type template is required
	- ViewResult: a page request template is required with the template rendering output surface annotated

## Required Output per Entry

- route_id
- Entry type (HTTP / HUB / GRAPHQL / WCF)
- Method and path or operation name
- Handler location
- Parameter sources (Route / Query / Body / Header / Cookie / File / Message)
- Complete request template or invocation template

For HTTP Controller / API entries, the following must additionally be output:

- Controller name
- Action name
- Route declaration method (Attribute / Conventional / Mixed)
- API version information (if any)
- Area (if any)
- Parameter binding source details (FromRoute / FromQuery / FromBody / FromForm / FromHeader / FromServices / CustomBinder)
- Return type template category (JSON / File / Redirect / View / Content)

## Workflow (Input → Execution → Output)

1. Input: read `source_path` and upstream artifacts (e.g. `route_mapping` / `route_tracer` / `framework_audit`), confirm dependencies are available and timestamps are consistent.
2. Execution: complete the audit in the order "shared grabber index → this specialty's enumeration rules → evidence point references", recording hit points, evidence chains, and unclosed paths.
3. Output: write to the agreed path per the "Output" section of this file; conclusions must be annotated `Confirmed` / `⚠️Pending Verification`, with a missing-evidence list attached.

## Checkpoint Design (Mandatory)

- 🔴 **CHECKPOINT A (Coverage Completeness Confirmation)**: before output, confirm that entries have not been trimmed by "high-risk first".
- 🔴 **CHECKPOINT B (Route Closure Confirmation)**: must confirm Controllers/Actions correspond one-to-one with final paths, methods, and route_ids.
- 🔴 **CHECKPOINT C (Parameter Binding Confirmation)**: must confirm binding sources and return type templates of key entries are expanded.
- 🛑 **STOP**: if unmapped entries exist or route_ids are inconsistent, declaring route mapping complete is forbidden.
- 🔴 **CHECKPOINT D (Count Reconciliation Self-Check)**: the routes file count reconciliation section is complete (declared_route_count / expanded_route_count / count_self_check); when count_self_check=FAIL, entering route-tracer is forbidden; fix the counts first.

## Failure Scenarios and Fallbacks (if-then)

| Trigger Condition | First-Line Handling | Fallback if Still Failing |
|---|---|---|
| Controller/Action to final path mapping not closed | Backfill attribute + conventional combination evidence | Mark as incomplete and output the missing entry list |
| Parameter binding source expansion incomplete | Fill in FromRoute/Query/Body/Form/Header/Services | Do not proceed with downstream linkage; keep pending-mapping items first |
| route_id inconsistent with downstream artifacts | Fix routes/params numbering consistency first | Continuing the trace phase is forbidden; output remediation steps |

🔴 **STOP: when any fallback is triggered, declaring route mapping complete is forbidden.**

## Do NOT Do (Anti-Pattern Blacklist)

## Handler Location (Mandatory)

Each entry must give handler source evidence:

- File path
- Class name, method name, signature
- For Controllers, the ControllerClass.ActionMethod form is mandatory
- If the path comes from a conventional route, the corresponding route template location in Program.cs / Startup.cs must be given
- If generated by a framework convention, the convention source should be stated rather than only the final path

## Executable Parameters and Output Templates (Mandatory)

- Audit conclusion level: `Confirmed` / `⚠️Pending Verification` / `Not Applicable` (choose exactly one; leaving blank is forbidden).
- Minimum evidence set: must include at least the five items `entry point`, `controllable parameters`, `key calls`, `security boundary`, `missing evidence`.
- Output file naming: uniformly use `{topic}_{timestamp}.md`, aligned with `IO_PATH_CONVENTION.md`.
- Softening wording is forbidden: e.g. "possibly at risk / worth noting / depends on the situation / very likely"; when evidence is insufficient, must explicitly write `⚠️Pending Verification` and the next follow-up confirmation action.

Minimal output snippet (directly reusable):

```md
- Audit conclusion level: Confirmed
- Minimum evidence set: entry point=...; controllable parameters=...; key calls=...; security boundary=...; missing evidence=none
- Next action: if gaps exist, supplement parameter propagation evidence for trace_id=...
```

## Output Format (Mandatory)

- The standard skeletons of routes_{timestamp}.md, params_{timestamp}.md, and quality/route_mapper_validation_{timestamp}.md are governed by shared/DOTNET_ROUTE_OUTPUT_TEMPLATES.md
- This Skill assigns route_ids only to HTTP / Controller-type entries: use the N of `=== [N] ... ===` in routes_{timestamp}.md as the route_id, and require it to be consistent with params_{timestamp}.md, route_tracer/{route_id}/trace_{timestamp}.md, and the final summary report
- Non-HTTP synthetic entries such as CLI / hook / sink-only do not consume the [N] sequence numbers of this file; such synthetic route_ids are uniformly carried by cross_analysis/high_risk_routes_{timestamp}.md consumed by dotnet-audit-pipeline, for subsequent route-tracer bucketing
- If the project needs extra fields, they may be appended after the standard skeleton, but core sections and key fields defined by the shared templates must not be removed

### Return Template Differences (Mandatory)

For Controller / API Actions, the template must be selected according to the return type:

1. JsonResult / ActionResult<T>
	- Output the standard HTTP/JSON request template
2. FileResult / PhysicalFileResult / VirtualFileResult
	- Output the download-type request template, annotating the download file name, content type, and path source
3. RedirectResult / LocalRedirectResult / RedirectToActionResult
	- Output the request template that triggers the redirect, annotating the ReturnUrl / next parameters that may be affected
4. ViewResult / PartialViewResult
	- Output the page request template, annotating that this Action enters the view rendering chain
5. ContentResult
	- Output the plain text or custom content-type request template
