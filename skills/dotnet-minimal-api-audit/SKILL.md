## Key Checks

- **Routes and endpoint registration**: MapGet/MapPost/MapPut/MapDelete/MapPatch, MapGroup/RouteGroupBuilder, WithTags/WithName/WithOpenApi, route templates, HTTP method constraints, prefix inheritance behavior
- **Parameter binding**: [FromQuery], [FromRoute], [FromBody], [FromForm], [FromHeader], automatic binding rules, BindAsync, TryParse, IParsable<T>, Records as DTOs
- **Lambda handlers**: inline lambda vs static method vs local function closure capture, variable scope, closure escape of security-sensitive operations
- **Endpoint filters**: IEndpointFilter implementations, EndpointFilterContext, EndpointFilterInvocationBehavior, filter registration and execution order, authorization and exception filters
- **Result filtering**: Results factory methods, Results.Extensions, IResult implementations, streaming vs complete responses, content negotiation
- **Authentication and metadata**: .RequireAuthorization(), anonymous endpoints, metadata propagation, route group inheritance, WithMetadata, IAuthorizeData
- **OpenAPI integration**: AddOpenApi, OpenApiRequestBody/Response, SwaggerGen integration, XML comment exposure
- **File and stream handling**: IFormFile binding, Stream returns, File(Permission) and PhysicalFile usage, path traversal danger
- **Minimal API-specific risks**: global filter blind spots with no Controller classes, missing parameter validation with no ActionFilters, CSRF window with no [ValidateAntiForgeryToken], missing explicit registration in Startup.Configure

## Enumeration Rules (Mandatory Refinement)

- **Endpoint registration enumeration**:
  - Search keywords: MapGet, MapPost, MapPut, MapDelete, MapPatch, MapGroup, RouteGroupBuilder, WithTags, WithName, WithOpenApi, RequireAuthorization, DisableAutoAcceptAuthorization
  - Record: route template, HTTP method, group prefix, endpoint filters, authentication requirements, metadata types
  - Identify route group prefix inheritance behavior, WithGroupName vs MapGroup prefix differences

- **Parameter binding enumeration**:
  - Search keywords: [FromQuery], [FromRoute], [FromBody], [FromForm], [FromHeader], BindAsync, TryParse, IParsable<T>, ParsableEndpointFilter
  - Record: binding source, parameter name, default value, nullability, Records types, complex object expanded fields
  - Identify implicit vs explicit binding differences, default behavior on binding failure

- **Lambda handler enumeration**:
  - Search keywords: app.MapGet.*lambda, delegate, Func<HttpContext, ...>, Func<...Request, ...Response>, async (ctx =>
  - Record: variables captured by the lambda, service injection in closures, static members vs instance members, closure sources of security-sensitive operations
  - Identify request/response data flow in inline lambda handlers

- **Endpoint filter enumeration**:
  - Search keywords: IEndpointFilter, EndpointFilterContext, EndpointFilterDelegate, AddEndpointFilter, EndpointFilterInvocationBehavior
  - Record: filter type (sync/async), registration position, execution order (PipelineOrderFilter), parameter reading, return value modification, exception handling
  - Identify intersections of authorization filters, metadata filters, and logging filters

- **Result filtering enumeration**:
  - Search keywords: Results.Ok, Results.NotFound, Results.Extensions, IResult, ExecuteAsync, IStatusCodeHttpWriter
  - Record: result type, status code, content negotiation, streaming vs complete responses, Results.Extensions custom implementations
  - Identify Results<T> generic wrapping, implicit conversions, ProblemDetails integration

- **Metadata and authentication enumeration**:
  - Search keywords: WithMetadata, IAuthorizeData, AuthorizeAttribute, AllowAnonymousAttribute, EndpointMetadataCollection
  - Record: authorization policy names, role/claim requirements, anonymous exceptions, endpoint priority
  - Identify metadata override rules inherited from route groups

- **OpenAPI enumeration**:
  - Search keywords: AddOpenApi, OpenApiRequestBody, OpenApiResponse, AddSwaggerGen, AddEndpointsApiExplorer, IncludeXmlComments
  - Record: request body types, response types, XML comment exposure, tag grouping, version differences
  - Identify sensitive field exposure in OpenAPI documents

- **File handling enumeration**:
  - Search keywords: IFormFile, IFormFileCollection, File(Permission), PhysicalFile, Path.Combine, ExtractToDirectory, archive
  - Record: file save path, extension validation, MIME type, content disposition, landing point
  - Identify path traversal risks, zip bombs, filename injection

- For each endpoint record: route template, HTTP method, parameter binding method, handler type (lambda/method), filter chain, authentication metadata, return type, OpenAPI visibility, and intersection points with vulnerability specialties

## Barrier Verification Matrix (Mandatory)

Assess against the fail-close three-tier standard in `DOTNET_AUDIT_EXECUTION_STANDARD.md`:

| Tier | Check Item | Pass Criteria | Failure Degradation |
|------|--------|----------|----------|
| Tier 1 | Minimal API endpoint exists and is reachable | MapGet/MapPost/MapPut/MapDelete/MapPatch exist and are externally reachable | BLOCKED → no reachable Minimal API endpoint; the specialty is deprioritized |
| Tier 2 | Parameter binding/filter has a bypass | Implicit binding causes over-posting, EndpointFilter execution order is wrong, or a lambda closure captures sensitive data | BLOCKED → binding and filter chains are complete with no bypass; conclusion degraded |
| Tier 3 | Authentication missing/metadata propagation enables exploitation | RequireAuthorization missing, route group metadata inheritance error, anonymous endpoint exposes sensitive operations | PARTIAL → only potential risks and verification steps are output |

## Two-Phase Determination Flow (Mandatory)

- **Phase 1 (Initial Screening Hit)**: Minimal API endpoint + parameter binding/filter + authentication/metadata hit; output `Hit ID: M{hash}`.
- **Phase 2 (Refined Confirmation)**:
  1. Trace in reverse: Map* endpoint → route group inheritance → parameter binding → EndpointFilter chain;
  2. Verify implicit-binding over-posting, EndpointFilter order, lambda closure sensitive data capture;
  3. Assess the correctness of RequireAuthorization/AllowAnonymous and route group metadata inheritance;
  4. If all three barrier tiers pass → `Confirmed Vulnerability`; if any fails → degrade per the matrix.

## Determination Rules and Priority (Mandatory)

1. **Confirmed Vulnerability**: endpoint reachable + parameter binding/filter bypass + authentication missing/metadata propagation error. Output `Confirmed Vulnerability`.
2. **Pending Confirmation**: endpoint/binding/authentication evidence partially exists, but filter execution order or metadata inheritance cannot be proven. Output `Pending Confirmation`.
3. **False Positive / No Risk**: endpoint unreachable or protected, binding explicit with complete validation, EndpointFilter order correct, authentication metadata has no inheritance errors. Output `False Positive` with determination basis.

## Testing Suggestions and Minimum Trigger Conditions (Mandatory)

- **Minimum Trigger Conditions**:
  - A Minimal API endpoint exists (MapGet/MapPost/MapPut/MapDelete/MapPatch)
  - The endpoint is externally reachable and accessible anonymously or with weak authentication
  - Or implicit parameter binding causes over-posting
  - Or EndpointFilter execution order is wrong, or a lambda closure captures sensitive data
- **Test Case Suggestions**:
  - Happy Path: a normal Minimal API request is processed through complete binding and filters with correct authentication
  - Edge/Ambiguity: MapGroup metadata inheritance override, implicit binding field injection, lambda closure variable escape, IFormFile path traversal, CSRF window (no Antiforgery)
- Each hit output appends `Hit ID: M{hash}` and `test_id: T{hash}` for traceability.

## Workflow (Input → Execution → Output)

1. Input: read `source_path` and upstream artifacts (e.g. `route_mapping` / `route_tracer` / `framework_audit`), confirm dependencies are available and timestamps are consistent.
2. Execution: complete the audit in the order "shared grabber index → this specialty's enumeration rules → evidence point references", recording hit points, evidence chains, and unclosed paths.
3. Output: write to the agreed path per the "Output" section of this file; conclusions must be annotated `Confirmed` / `⚠️Pending Verification`, with a missing-evidence list attached.

## Checkpoint Design (Mandatory)

- 🔴 **CHECKPOINT A (Endpoint Confirmation)**: Map* endpoints, route group inherited metadata, and authentication requirements must be confirmed first.
- 🔴 **CHECKPOINT B (Binding and Filter Confirmation)**: the parameter binding chain and EndpointFilter execution chain must be confirmed.
- 🔴 **CHECKPOINT C (Side-Effect Confirmation)**: whether the lambda/handler triggers sensitive downstream operations must be stated.
- 🛑 **STOP**: if endpoint metadata and the execution chain are not closed, the conclusion is degraded to `⚠️Pending Verification / Environment-Dependent`.

## Failure Scenarios and Fallbacks (if-then)

| Trigger Condition | First-Line Handling | Fallback if Still Failing |
|---|---|---|
| Map* endpoint inventory and metadata incomplete | Fill in route group inheritance, authorization, and filter chains | Degrade to `⚠️Pending Verification / Environment-Dependent` |
| Parameter binding source unclear | Analyze explicit/implicit binding and failure default behavior | Do not output a strong conclusion yet; give only a verification path |
| Handler side-effect chain not closed | Trace to sensitive downstream calls and response paths | Describe the risk conservatively and keep it pending confirmation |

🔴 **STOP: when any fallback is triggered, outputting "confirmed safe" is forbidden.**

## Do NOT Do (Anti-Pattern Blacklist)

- Anti-pattern: enumerating only Map* without tracing the filter chain. Correct approach: fill in the EndpointFilter and authorization metadata execution order.
- Anti-pattern: ignoring implicit parameter binding. Correct approach: make binding sources and failure default behavior explicit.
- Anti-pattern: mixing anonymous endpoints with internal endpoints. Correct approach: group by boundary and assess separately.
- Anti-pattern: drawing strong conclusions before the execution chain is closed. Correct approach: degrade to `⚠️Pending Verification / Environment-Dependent`.

Output type mapping: AUTH, DESER, CFG, LOGIC, CSRF, FILE, SQL, SSRF, XSS.
