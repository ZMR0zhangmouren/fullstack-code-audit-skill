# ASP.NET Core Framework Specialty Audit

## Shared Grabber Index Reference

- By default, use shared/DOTNET_AUDIT_GRABBER_INDEX.md as the basic retrieval index for this skill
- By default, use shared/DOTNET_SINK_REFERENCE.md as the baseline for this specialty's Sink type definitions and trace-gate validation
- By default, follow the general execution standard of `skills/shared/DOTNET_AUDIT_EXECUTION_STANDARD.md` (two-phase determination, fail-close determination, testing requirements)
- Enumeration must at least cover the aspnet-core-related grabbers of entry definitions, binding / conversion, precondition controls, sensitive operations, and security configuration
- If the project has framework secondary encapsulation, unified extension methods, a platform foundation, or a host wrapper layer, they must be added to the project-internal grabbers section of the output
- When this skill's specialty enumeration rules are finer-grained than the shared index, this skill takes precedence, but the shared index's basic coverage must not be reduced

## Input Dependencies

- Required: `source_path`
- Optional: `route_mapping/routes_{timestamp}.md` and `route_mapping/params_{timestamp}.md` (if already generated by `dotnet-route-mapper`, used to align entries, parameter bindings, and `route_id`)
- Optional: `auth_audit/auth_mapping_{timestamp}.md` (if alignment of anonymous entries, P0 / P1 bucketing, and authorization boundaries is needed)
- Optional: `route_tracer/{route_id}/trace_{timestamp}.md` and `route_tracer/{route_id}/trace_summary_{timestamp}.md` (if cross-referencing the middleware / host control plane with specific entries and side-effect chains is needed)

## Key Checks

- Middleware order: the ordering relationships among UseForwardedHeaders, UsePathBase, UseRouting, UseCors, UseAuthentication, UseAuthorization, UseSession, and UseEndpoints
- The configuration and coverage of Antiforgery, CORS, static files, exception pages, security headers, HSTS, HTTPS redirection, Rate Limiting, and Output Caching
- Minimal API, Endpoint Filters, Route Groups, MapFallback, MapWhen, branch pipelines, and the mixing boundary of anonymous / authorized endpoints
- appsettings.json, web.config, Options binding, IOptionsSnapshot, IOptionsMonitor, custom configuration binders, and model validation gaps
- Trust boundaries and environment differences of Kestrel, IIS, reverse proxies, containers, PathBase, HostFiltering, and ForwardedHeaders
- The exposure surface of functional components such as Swagger, HealthChecks, Prometheus, Hangfire, SignalR, StaticFile, and Razor Runtime Compilation

## Enumeration Rules (Mandatory Refinement)

- Enumerate middleware registration order in Program.cs, Startup.cs, extension methods, and host initialization code, recording the entry conditions, order positions, and short-circuit presence of each Use / Map / Run branch
- Search appsettings.json, web.config, UseRouting, UseAuthentication, UseAuthorization, UseCors, UseSession, UseEndpoints, MapGroup, MapControllers, MapFallback, MapWhen, UseWhen, AddAntiforgery, AddCors, AddAuthentication, and AddAuthorization first
- Enumerate exposed endpoints of Minimal APIs, Controller Endpoints, HealthChecks, Swagger, StaticFiles, Hangfire, SignalR, GraphQL, and Prometheus, recording anonymous reachability, environment switches, and PathBase and reverse-proxy prefix effects
- Enumerate Options binding, Configure<T>, PostConfigure<T>, BindConfiguration, custom validators, IValidateOptions, environment variable overrides, and appsettings.* layering, recording whether security switches can be overridden at runtime
- For each high-risk component record: registration location, protection mechanism, dependent configuration, environment differences, preceding middleware, following middleware, and the vulnerability types it may affect

## Barrier Verification Matrix (Mandatory)

Evaluate per the fail-close three-level standard of `DOTNET_AUDIT_EXECUTION_STANDARD.md`:

| Level | Check Item | Pass Criteria | Failure Degradation |
|------|--------|----------|----------|
| Level 1 | critical middleware chain order defects | key security middleware (Auth / AuthZ / CORS / Antiforgery) is out of order or has short-circuit branches, causing security controls to fail | BLOCKED → middleware order correct with no short-circuits; the specialty is downgraded to low priority |
| Level 2 | exposure surface has anonymously reachable high-risk endpoints | endpoints such as Swagger / HealthChecks / Hangfire / StaticFiles / SignalR / GraphQL are anonymously reachable in the target environment without additional protection | BLOCKED → all high-risk endpoints are authenticated or unreachable in the environment |
| Level 3 | configuration overrides disable security switches | security switches (HTTPS / HSTS / RateLimit / OutputCache) are overridden off at runtime by environment variables / code / layered configuration | PARTIAL → only output configuration difference hypotheses and verification steps |

## Two-Phase Determination Process (Mandatory)

- **Phase 1 (initial screening hit)**: hit a critical middleware order defect, an anonymously reachable endpoint, or a configuration override point, and output `hit ID: M{hash}`.
- **Phase 2 (refined confirmation)**:
  1. back-trace the middleware registration order and branch entry conditions, confirming whether the security control actually fails;
  2. verify the real reachability and protection mechanisms of exposed endpoints in the target deployment environment;
  3. align the final effective values of the configuration override chain (appsettings.json → environment variables → runtime code);
  4. if all three-level Barriers pass → `Confirmed Vulnerability`; if any fails → degrade per the matrix.

## Determination Rules and Priorities (Mandatory)

1. **Confirmed Vulnerability**: middleware order defect causing security control failure + exposure surface anonymously reachable + configuration switches overridden off. Output `Confirmed Vulnerability`.
2. **Pending**: middleware / exposure surface / configuration evidence partially exists, but the deployment environment or runtime behavior cannot be confirmed. Output `Pending`.
3. **False Positive / No Risk**: middleware order correct, exposure surface protected, and security switches effective and not overridden. Output `False Positive` with the determination basis.

## Testing Recommendations and Minimal Trigger Conditions (Mandatory)

- **Minimal trigger conditions**:
  - an ASP.NET Core application exists (Program.cs / Startup.cs, etc.)
  - the middleware registration order has critical security control (Auth / AuthZ / CORS / Antiforgery) order errors
  - or anonymously reachable high-risk endpoints exist (Swagger / HealthChecks / Hangfire, etc.)
  - or security switch configurations are overridden off at runtime
- **Test case suggestions**:
  - Happy Path: normal requests are processed in the correct middleware order and security controls take effect
  - Boundary / ambiguity: MapWhen / UseWhen branch short-circuits, Development / Production configuration differences, PathBase and reverse-proxy prefix effects
- Each hit output appends `hit ID: M{hash}` and `test_id: T{hash}` for traceability.

## Executable Parameters and Output Templates (Mandatory)

- Audit conclusion levels: `Confirmed` / `⚠️Pending Verification` / `Not Applicable` (choose one of three; blank is forbidden).
- Minimum evidence set: at least the five items `Entry Point`, `Controllable Parameter`, `Key Call`, `Security Boundary`, and `Missing Evidence`.
- Output file naming: uniformly use `{topic}_{timestamp}.md`, aligned with `IO_PATH_CONVENTION.md`.
- Softened wording is forbidden: such as "may be at risk / suggested attention / depends on the situation / most likely"; when evidence is insufficient, `⚠️Pending Verification` and the next evidence-supplementing action must be explicitly written.

Minimal output fragment (directly reusable):

```md
- Audit conclusion level: Confirmed
- Minimum evidence set: entry point=...; controllable parameter=...; key call=...; security boundary=...; missing evidence=none
- Next action: if gaps exist, supplement the parameter-propagation evidence of trace_id=...
```

- Output file: framework_audit/aspnet_core_{timestamp}.md
- Results must be organized into four sections: middleware order, endpoint exposure surface, configuration binding and security switches, and environment differences and proxy boundaries
- Every issue point must state: code location, trigger conditions, impact scope, associated endpoints / functional components, and the vulnerability specialties recommended for joint review
- Unclosed chains and environment-dependent items must be listed separately, stating whether what is missing is configuration evidence, deployment evidence, proxy evidence, or runtime registration evidence

## Workflow (Input → Execution → Output)

1. Input: read `source_path` and upstream artifacts (such as `route_mapping` / `route_tracer` / `framework_audit`), confirming dependencies are available and timestamps consistent.
2. Execution: complete the audit in the order "shared grabber index → this specialty's enumeration rules → evidence point references", recording hit points, evidence chains, and unclosed paths.
3. Output: persist to the agreed paths per the "Output" section of this file; conclusions must be annotated `Confirmed` / `⚠️Pending Verification`, with a missing evidence list attached.

## Checkpoint Design (Mandatory)

- 🔴 **CHECKPOINT A (middleware chain confirmation)**: the order and branch entry conditions of key middleware must be confirmed.
- 🔴 **CHECKPOINT B (exposure surface confirmation)**: anonymously reachable endpoints and the effective scope of environment switches must be confirmed.
- 🔴 **CHECKPOINT C (configuration closure confirmation)**: the final runtime configuration values or override order evidence must be given.
- 🛑 **STOP**: if middleware / configuration evidence is not closed, the conclusion is downgraded to `⚠️Environment-Dependent`.

## Failure Scenarios and Fallbacks (if-then)

| Trigger Condition | First-Line Handling | Fallback on Continued Failure |
|---|---|---|
| middleware order cannot be closed (branches / MapWhen / short-circuits unclear) | complete the full pipeline order and branch entry conditions | downgrade the conclusion to `⚠️Environment-Dependent` and annotate the missing evidence |
| configuration override chain incomplete (files / environment variables / runtime code) | align the final effective values and override priorities | output only pending items; strong "safe" conclusions are forbidden |
| production vs development environment boundary unclear | give evidence and conclusions per environment separately | adopt the most conservative criteria and retain review recommendations |

🔴 **STOP: when any fallback triggers, outputting "safe" is forbidden.**

## Overall Architecture and Redundancy Control (Mandatory)

- Section organization must keep the three-layer skeleton: `input constraints` → `execution steps` → `output and acceptance`; missing layers or cross-layer mixing are forbidden.
- A single paragraph is recommended not to exceed 6 lines; synonymous rules must not appear more than twice; duplicated content must be merged into the single-source-of-truth section.

## Quality Gate & Assessment Consistency (Mandatory)

- Execute the minimal gate self-check before output: `input completeness`, `key evidence hit`, and `output path valid` must all be PASS.
- If any of `key evidence missing`, `chain not closed`, or `consistency_check_status=BLOCKED` exists, the conclusion must be downgraded to `BLOCKED`; outputting "Confirmed Exploitable / Deliverable" is forbidden.
- The report must explicitly record: `gate_status`, `blocked_reasons`, `recheck_action`, and be traceably aligned with `quality/*` artifacts.

## Do NOT Do (Anti-Pattern Blacklist)

- Anti-pattern: treating registration code as runtime-effective fact. Correct practice: also verify environment branches, configuration overrides, and final execution paths.
- Anti-pattern: ignoring the impact of middleware order on authentication / rate limiting / CORS. Correct practice: order evidence and short-circuit branches must be given.
- Anti-pattern: extrapolating development-environment security switch conclusions directly to production. Correct practice: the Development / Production boundary must be explicit.
- Anti-pattern: outputting "safe" with an unclosed evidence chain. Correct practice: downgrade to `⚠️Environment-Dependent` and annotate the missing evidence.

Output type mapping: AUTH, CSRF, CFG, XSS, LOGIC, SESS.
