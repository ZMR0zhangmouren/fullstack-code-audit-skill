# .NET Framework Specialty Skill Template

This template is used to create new dotnet-{framework}-audit framework specialty skills.

## Usage Instructions

- Replace {framework} with the specific framework or runtime subdomain
- Framework specialties are by default used to describe framework boundaries, runtime control planes, host differences, and component exposure surfaces — not to replace vulnerability specialties
- By default, integrate shared/DOTNET_AUDIT_GRABBER_INDEX.md, shared/EVIDENCE_POINT_IDS.md, shared/IO_PATH_CONVENTION.md, shared/SEVERITY_RATING.md, shared/DOTNET_SINK_REFERENCE.md
- You must explicitly write out `## Input Dependencies`; do not leave the relationships among `source_path`, `route_mapping/*`, `auth_audit/*`, `route_tracer/*` as implicit conventions
- Framework specialties take `source_path` as a required input by default; if `dotnet-route-mapper` artifacts already exist, list `route_mapping/routes_{timestamp}.md` and `route_mapping/params_{timestamp}.md` as optional inputs to align entry points, parameter bindings, and `route_id`
- If the framework specialty involves anonymous entry points, P0/P1 bucketing, authorization metadata, or resource-ownership boundaries, list `auth_audit/auth_mapping_{timestamp}.md` as an optional input
- If the framework specialty needs to cross-reference middleware, component, and control-plane risks with specific entry points and side-effect chains, list `route_tracer/{route_id}/trace_{timestamp}.md` and `route_tracer/{route_id}/trace_summary_{timestamp}.md` as optional inputs
- If the framework specialty affects strong vulnerability conclusions, you must explicitly state how it is consumed by route_tracer, vuln_audit, and dotnet-audit-pipeline

## Minimum Acceptance Requirements

- Name, description, and responsibility boundaries are clear
- The shared grabber index and other necessary shared rules are referenced
- The four-layer structure exists: input dependencies + key checks + enumeration rules + output requirements
- The evidence reference criteria are stated
- The relationships with route_tracer / vuln_audit / pipeline are stated
- How to cross-reference `route_mapping/*`, `auth_audit/*`, `route_tracer/*` with the framework control plane is stated
- Output paths comply with shared/IO_PATH_CONVENTION.md
- Boundaries are distinguishable from existing framework specialties without large-scale overlapping responsibilities
