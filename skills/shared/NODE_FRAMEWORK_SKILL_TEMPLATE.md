# Node.js Framework Specialty Skill Template

This template is used to create new node-{framework}-audit framework specialty skills, serving as the drafting baseline for each framework specialty in the P2 Node.js full-stack extension.

## Usage Instructions

- Replace {framework} with the specific framework or runtime subdomain (e.g., express, nestjs, nextjs, koa, fastify, nuxt)
- Framework specialties are by default used to describe framework boundaries, runtime control planes, host differences, and component exposure surfaces — not to replace vulnerability specialties
- By default, integrate shared/NODE_AUDIT_GRABBER_INDEX.md, shared/NODE_SINK_REFERENCE.md, shared/SEVERITY_RATING.md, shared/IO_PATH_CONVENTION.md
- **By default, follow the general execution standard in shared/DOTNET_AUDIT_EXECUTION_STANDARD.md (two-phase determination, fail-close determination, hit ID conventions, testing requirements); the standard is stack-agnostic and is referenced directly by the Node.js side**
- You must explicitly write out `## Input Dependencies`; do not leave the relationships among `node_source_path`, `node/route_mapping/*`, `node/auth_audit/*`, `node/route_tracer/*` as implicit conventions
- Framework specialties take `node_source_path` as a required input by default; if `node-route-mapper` artifacts already exist, list `node/route_mapping/routes_{timestamp}.md` and `node/route_mapping/params_{timestamp}.md` as optional inputs to align entry points, parameter bindings, and `route_id`
- If the framework specialty involves anonymous entry points, P0/P1 bucketing, authorization metadata, or resource-ownership boundaries, list `node/auth_audit/auth_mapping_{timestamp}.md` as an optional input
- If the framework specialty needs to cross-reference middleware, component, and control-plane risks with specific entry points and side-effect chains, list `node/route_tracer/{route_id}/trace_{timestamp}.md` and `node/route_tracer/{route_id}/trace_summary_{timestamp}.md` as optional inputs
- If the framework specialty involves SSR, BFF forwarding, or frontend-backend isomorphic logic, list `cross/api_contract_map_{timestamp}.md` as an optional input
- If the framework specialty affects strong vulnerability conclusions, you must explicitly state how it is consumed by route_tracer, vuln_audit, and node-audit-pipeline
- If the framework specialty requires new EVID_NODE_* IDs or new shared grabbers, update shared first and then land the skill

## Two-Phase Determination (Mandatory)

This specialty follows the two-phase determination process in shared/DOTNET_AUDIT_EXECUTION_STANDARD.md:

> The general execution standard takes shared/AUDIT_EXECUTION_COMMON.md as its source of truth (shared evolution decision 3); this section retains node-stack-specific differences.

### Phase 1: Interim Conclusion

For each hit, first give one of three interim conclusions:

- `Confirmed Risk Candidate`: missing framework configuration or control plane may allow external input to bypass, privilege escalation, or sensitive information exposure
- `Pending`: the context shows a suspicious pattern, but the entry coverage, barrier behavior, or call chain is unclear
- `False Positive`: the configuration has fail-close explicitly enabled, or the risk point is already covered by another control plane

### Phase 2: Mandatory Evidence Chasing

If Phase 1 is "Pending", you must continue chasing at least one more hop of the call chain or downstream parser until any of the following holds:

- Evidence is found linking the framework control plane to a specific entry/sink → `Confirmed Risk`
- Fixed whitelist mapping / fail-close evidence is found → `False Positive`
- A key call chain is still missing → remain `Pending`, but you must state which hop is missing

**fail-close semantics**: barriers, whitelists, validators, and filters must be evaluated in their failure mode. Unknown/illegal input must throw an exception, return empty, refuse execution, or trigger a log alert — it must never pass through the raw value; any silent-fallback or fail-open behavior is treated as high risk.

## Minimum Acceptance Requirements

- Name, description, and responsibility boundaries are clear
- shared/NODE_AUDIT_GRABBER_INDEX.md, shared/NODE_SINK_REFERENCE.md, shared/DOTNET_AUDIT_EXECUTION_STANDARD.md, shared/SEVERITY_RATING.md, shared/IO_PATH_CONVENTION.md are referenced
- The complete ten-layer structure exists: shared grabber index reference + input dependencies + key checks + enumeration rules (mandatory refinement) + Barrier verification matrix (mandatory) + two-phase determination (mandatory) + determination rules (mandatory refinement) + testing recommendations (mandatory) + evidence references + output
- The dotnet version's three-layer structure is retained: framework boundary layer / runtime configuration layer / precondition control plane layer
- .NET concepts have been replaced with Node.js counterparts (middleware chains, Guard/Interceptor, helmet/CORS, session store, SSR configuration)
- The evidence reference criteria are stated (including EVID_NODE_* placeholders or real evidence points)
- The relationships with node/route_tracer / node/vuln_audit / pipeline / cross stack are stated
- How the framework specialty is consumed by route_tracer, vuln_audit, and pipeline is stated
- The Barrier verification matrix header is exactly `| Barrier Type | Typical Implementation | Verification Action | Determination Criteria |`
- Output paths comply with shared/IO_PATH_CONVENTION.md and are explicitly written as `node/framework_audit/{framework}_{timestamp}.md`
- Boundaries are distinguishable from existing framework specialties without large-scale overlapping responsibilities
