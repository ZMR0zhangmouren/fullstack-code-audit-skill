# SignalR Framework Specialty Audit

## Shared Grabber Index Reference

- By default, use shared/DOTNET_AUDIT_GRABBER_INDEX.md as the basic retrieval index for this skill
- By default, use shared/DOTNET_SINK_REFERENCE.md as the baseline for this specialty's Sink type definitions and trace-gate validation
- By default, follow the general execution standard of `skills/shared/DOTNET_AUDIT_EXECUTION_STANDARD.md` (two-phase determination, fail-close determination, testing requirements)
- Enumeration must at least cover the signalr-related grabbers of entry definitions, binding / conversion, precondition controls, sensitive operations, and security configuration
- If the project has framework secondary encapsulation, unified extension methods, a platform foundation, or a host wrapper layer, they must be added to the project-internal grabbers section of the output
- When this skill's specialty enumeration rules are finer-grained than the shared index, this skill takes precedence, but the shared index's basic coverage must not be reduced

## Input Dependencies

- Required: `source_path`
- Optional: `route_mapping/routes_{timestamp}.md` and `route_mapping/params_{timestamp}.md` (if already generated by `dotnet-route-mapper`, used to align Hub methods, parameter sources, and `route_id`)
- Optional: `auth_audit/auth_mapping_{timestamp}.md` (if alignment of connection establishment, Hub authorization, and tenant / room boundaries is needed)
- Optional: `route_tracer/{route_id}/trace_{timestamp}.md` and `route_tracer/{route_id}/trace_summary_{timestamp}.md` (if cross-referencing Hub methods with downstream side-effect chains such as databases, files, templates, and notifications is needed)

## Key Checks

- [Authorize] / policy / role / claim checks on Hub methods, IUserIdProvider, custom HubFilters, claims mapping at connection establishment, and permission validation
- group join / leave, broadcast targets, tenant isolation, room boundaries, presence states, and cross-connection message visibility
- binding relationships among ConnectionId, UserIdentifier, Context.Items, query string tokens, cookie flags / JWT validation parameters, and access tokens
- impact of client message parameter validation, model binding, streaming uploads, binary messages, and retry mechanisms on server-side side effects
- authorization and state consistency issues caused by Backplanes, Redis, Azure SignalR, sticky sessions, scale-out, and connection migration
- whether Hub methods trigger high-value operations such as databases, files, commands, templates, and notifications without additional constraints

## Enumeration Rules (Mandatory Refinement)

- Enumerate all Hubs, Hub methods, HubFilters, IUserIdProviders, OnConnectedAsync, OnDisconnectedAsync, group management logic, and client callback methods
- Search Hub, SendAsync, Groups.AddToGroupAsync, Clients.All, Clients.User, Clients.Group, Authorize, HubFilter, Context.UserIdentifier, and access_token first
- Enumerate connection establishment parameters, query string tokens, cookie authentication, claims mapping, group name construction, tenant identifier concatenation, and room join conditions
- Enumerate server-side side-effect methods: database writes, file operations, task dispatch, notification pushes, template rendering, and admin actions, recording whether they rely only on connection state without business authorization
- For each Hub method record: call direction, parameter source, authorization method, target broadcast scope, state dependencies, scale-out impact, and subsequent side effects

## Barrier Verification Matrix (Mandatory)

Evaluate per the fail-close three-level standard of `DOTNET_AUDIT_EXECUTION_STANDARD.md`:

| Level | Check Item | Pass Criteria | Failure Degradation |
|------|--------|----------|----------|
| Level 1 | Hub methods exist and connections can be established | Hub methods and OnConnectedAsync exist, and clients can actually establish connections and invoke them | BLOCKED → no user-reachable Hub entries; the specialty is downgraded to low priority |
| Level 2 | authorization / group management has bypasses | Hub methods / group joins lack [Authorize] or policy checks, or UserIdentifier / claims mapping can be forged | BLOCKED → authorization and group management complete without bypasses; the conclusion is downgraded |
| Level 3 | broadcasts / side effects unauthorized and reachable | SendAsync / Clients.All / Group broadcasts without business authorization, or Hub methods triggering high-value operations such as databases / files / commands | PARTIAL → only output potential risks and verification steps |

## Two-Phase Determination Process (Mandatory)

- **Phase 1 (initial screening hit)**: hit Hub methods / connection establishment + authorization / group management + broadcast / side-effect chains, and output `hit ID: M{hash}`.
- **Phase 2 (refined confirmation)**:
  1. back-trace the connection establishment → claims mapping → Hub method authorization chain;
  2. verify group join conditions, the UserIdentifier implementation, and the forgeability of claims mapping;
  3. assess the authorization boundary of broadcast scopes (Clients.All / Group / User) and downstream side effects (databases / files / commands);
  4. if all three-level Barriers pass → `Confirmed Vulnerability`; if any fails → degrade per the matrix.

## Determination Rules and Priorities (Mandatory)

1. **Confirmed Vulnerability**: Hub entry reachable + authorization / group management bypass + unauthorized broadcasts / side effects. Output `Confirmed Vulnerability`.
2. **Pending**: Hub / authorization / broadcast evidence partially exists, but scale-out / Backplane or claims mapping cannot be confirmed. Output `Pending`.
3. **False Positive / No Risk**: Hub methods all authorized, group management strict, broadcast scopes controlled, and downstream side effects with business authorization. Output `False Positive` with the determination basis.

## Testing Recommendations and Minimal Trigger Conditions (Mandatory)

- **Minimal trigger conditions**:
  - a SignalR Hub or Hub methods exist
  - clients can establish connections and invoke Hub methods
  - or Hub methods / groups lack authorization checks
  - or broadcasts / side effects lack business authorization
- **Test case suggestions**:
  - Happy Path: normal connection establishment and Hub invocations with correct authorization and broadcast scopes
  - Boundary / ambiguity: query string token forgery, group name injection, Backplane state inconsistency, and authorization drift from scale-out connection migration
- Each hit output appends `hit ID: M{hash}` and `test_id: T{hash}` for traceability.

## Workflow (Input → Execution → Output)

1. Input: read `source_path` and upstream artifacts (such as `route_mapping` / `route_tracer` / `framework_audit`), confirming dependencies are available and timestamps consistent.
2. Execution: complete the audit in the order "shared grabber index → this specialty's enumeration rules → evidence point references", recording hit points, evidence chains, and unclosed paths.
3. Output: persist to the agreed paths per the "Output" section of this file; conclusions must be annotated `Confirmed` / `⚠️Pending Verification`, with a missing evidence list attached.

## Checkpoint Design (Mandatory)

- 🔴 **CHECKPOINT A (Hub entry confirmation)**: Hubs, groups, and connection negotiation entries must be confirmed complete.
- 🔴 **CHECKPOINT B (identity and authorization confirmation)**: connection-state authentication and method-level authorization chains must be confirmed.
- 🔴 **CHECKPOINT C (message boundary confirmation)**: the boundary from client-pushed data to downstream processing must be confirmed.
- 🛑 **STOP**: if the connection authentication chain is not closed, no "safe to go live" conclusion may be given.

## Executable Parameters and Output Templates (Mandatory)

- Audit conclusion levels: `Confirmed` / `⚠️Pending Verification` / `Not Applicable` (choose one of three; blank is forbidden).
- Minimum evidence set: at least the five items `Entry Point`, `Controllable Parameter`, `Key Call`, `Security Boundary`, and `Missing Evidence`.
- Output file naming: uniformly use `{topic}_{timestamp}.md`, aligned with `IO_PATH_CONVENTION.md`.
- Softened wording is forbidden: such as "may be at risk / suggested attention / depends on the situation / most likely"; when evidence is insufficient, `⚠️Pending Verification` and the next evidence-supplementing action must be explicitly written.

Minimal output fragment (directly reusable):

```md
- Audit conclusion level: Confirmed
- Minimum evidence set: entry point=...; controllable parameter=...; key call=...; security boundary=...; missing evidence=none
- Next action: if gaps exist, supplement the parameter-propagation evidence of trace_id=...
```

## Failure and Degradation Branches (Mandatory)

| Trigger Condition | First-Line Handling | Fallback on Continued Failure |
|---|---|---|
| Hub methods reachable but the authentication chain incomplete | output method-level authorization and connection-state evidence | downgrade to PARTIAL; unauthorized confirmed conclusions are forbidden |
| group broadcast boundary unverifiable (multi-node / Backplane) | record single-node evidence and group key construction | mark `⚠️Environment-Dependent` and await joint debugging evidence |
| UserIdentifier mapping implementation unresolvable | list candidate implementations and registration points | retain candidate chains and downgrade when convergence is impossible |
| only SendAsync seen without business side-effect closure | output the broadcast path and impact surface | no high-risk conclusion; convert to pending |

🔴 **STOP: until the "connection identity → Hub method → target broadcast / side effect" chain is proven closed, outputting confirmed overreach is forbidden.**

|---|---|---|---|
