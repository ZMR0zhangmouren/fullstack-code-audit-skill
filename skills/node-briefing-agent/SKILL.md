# Node.js Candidate Parameter List (Briefing)

## Goal

Generate a **non-skippable parameter checklist** for each sink, turning "don't miss parameters" into an input that downstream Taint and vulnerability specialty phases must process item by item.

**Briefing does not judge whether parameters are safe; it is only responsible for listing them all.**

## Core Principles

- Briefing **only lists parameters and does not judge safety**
- Every parameter must be annotated with: source, the position where it enters the sink, and the barrier that needs verification downstream
- This checklist is the input of the vulnerability specialty; a missed parameter = downstream cannot verify it

## Shared Grabber Index Reference

- By default, use `shared/NODE_AUDIT_GRABBER_INDEX.md` as the basic retrieval index for this skill
- By default, follow the general execution standards of `shared/AUDIT_EXECUTION_COMMON.md` and `shared/DOTNET_AUDIT_EXECUTION_STANDARD.md` (stack-agnostic)

## Input

- `node/scan_audit/scan_{filename|module}_{timestamp}.md`: risks output by the Scan phase (including taint_candidates)
- `node/route_mapping/params_{timestamp}.md`: route parameter mapping (if it exists)
- `node/route_mapping/middleware_inventory_{timestamp}.md`: middleware inventory (confirming entry preconditions such as body parser / static directories)
- `node_source_path`: Node.js project source path

## Output Schema

### node/briefing/briefing_{sink_id}_{timestamp}.md

Each sink must have an independent checklist generated:

## Candidate Parameter List

| Candidate Parameter | Parameter Source | Position Entering the Sink | Parameter Type | Follow-up Checks (must be verified by the specialty phase) |
|---------|---------|-----------------|---------|---------------------------|
| `req.query.column` | Query parameter | SQL identifier position (knex.raw concatenation) | Structure position | Server-side field whitelist |
| `req.body.filter` | Body object | `collection.find(req.body.filter)` object passthrough | Query object | Schema validation / operator filtering |
| `req.body.config` | Body object | `lodash.merge(defaults, req.body.config)` merge target | Merge target | `__proto__` key filtering and prototype isolation |
| `req.query.url` | Query parameter | `axios.get(url)` URL slot | URL | SSRF allowlist and redirect policy |
| `req.params.template` | Route parameter | `ejs.render(template)` template expression | Template expression | Template source fixation |

### Parameter Source Classification

| Source Type | Description | Examples |
|---------|------|------|
| `REQUEST` | Directly from HTTP requests | `req.query` / `req.params` / `req.body` / `req.headers` / `req.cookies` / uploaded file names |
| `FRAMEWORK` | Framework-injected request-derived data | Next.js `getServerSideProps` `params/query/req`, NestJS `@Param/@Body/@Query` decorator parameters, tRPC input |
| `CONFIG` | From configuration | `.env`, `config/` modules, `package.json`, default value objects |
| `STORAGE_READ` | From persistent storage reads | database query results, Redis cache, session storage (note: may carry other users' input → second-order injection source) |
| `COMPUTED` | Generated by code computation | concatenation, `Object.keys` derivation, intermediate path resolution values |
| `CONSTANT` | Hardcoded constants | literal strings, enum values |

### Position Classification for Entering Sinks

| Position Type | Description | Risk Level |
|---------|------|---------|
| `VALUE_POSITION` | Value positions (WHERE condition values, LIKE values, comparison values) | Medium (depends on barrier) |
| `STRUCTURE_POSITION` | Structure positions (query field names, sort keys, object keys, table / collection names) | High (usually no barrier) |
| `QUERY_OBJECT` | Whole object passed into queries / merges (find(object), merge(object)) | High (NoSQL operators / prototype chain pollution) |
| `MERGE_TARGET` | Recursive merge target (prototype chain pollution surface) | High |
| `DIRECT_SQL_TEXT` | Entering SQL text directly | High |
| `COMMAND_ARGUMENT` | Command string or argument slot | High |
| `FILE_PATH` | File path (read / write / extract) | High |
| `URL` | URL / URI / proxy forwarding target | High |
| `TEMPLATE_EXPRESSION` | Template expression / render string | High |
| `EVAL_STRING` | eval / Function / vm execution string | High |
| `HEADER_VALUE` | Header value / Set-Cookie (CRLF surface) | Medium |
| `REDIRECT_TARGET` | Redirect target | Medium |

## Handoff to Downstream Specialty Phases

```
Briefing outputs checklist
    → the specialty phase verifies each parameter in the checklist item by item
    → prioritize verifying STRUCTURE_POSITION / QUERY_OBJECT / MERGE_TARGET parameters
    → verify the actual barrier behavior for VALUE_POSITION parameters
    → output hit conclusions and EVID evidence after verification
```

## Anti-Patterns (Forbidden)

- ❌ **Excluding parameters at the Briefing stage**: e.g., "`category_id` has been processed by `parseInt`, so it is not listed in the checklist"
- ❌ **Missing parameters**: e.g., listing only 2 parameters while the sink actually has 6 dynamic parameters
- ❌ **Vague parameter sources**: e.g., writing "from the request" without specifying whether it is `req.query` / `req.body` / `req.headers`
- ❌ **Not annotating the entry position**: e.g., writing only the parameter name without stating whether it is a value position, a structure position, a query object, or a merge target

## Quality Gate

- [ ] Every sink has an independent briefing_{sink_id}_{timestamp}.md
- [ ] The checklist lists all dynamic parameters in the sink with nothing missed
- [ ] Every parameter has a clear source, position, and follow-up check item
- [ ] No parameter is excluded prematurely
- [ ] The checklist is grouped by parameter type (STRUCTURE_POSITION / QUERY_OBJECT / MERGE_TARGET first)

## Output Paths

- `node/briefing/briefing_{sink_id}_{timestamp}.md` (one per sink)
- `node/briefing/index_{timestamp}.md` (batch master index)
