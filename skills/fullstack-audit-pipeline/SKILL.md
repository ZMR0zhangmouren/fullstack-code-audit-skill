# Full-Stack Code Security Audit Master Entry

Objective: for projects containing both a dotnet backend and a Node.js frontend/BFF, output a reviewable, fixable, and quantifiable full-stack white-box audit report. This skill is the single full-stack master orchestration entry, responsible for phase 0 dual-stack stack detection, dual-stack parallel scheduling, phase 6 cross-stack correlation, the four completion-state declarations, and the full-stack-level closing double-safety.

## Inputs

Provided by the user:

- `dotnet_source_path`: .NET backend project source code path (solution directory, repository root, or single project directory).
- `node_source_path`: Node.js frontend/BFF source code path (repository root or a directory containing `package.json`).
- `stack_mode`: `BOTH | DOTNET_ONLY | NODE_ONLY`, defaulting to `BOTH`.
  - `BOTH`: audit both stacks.
  - `DOTNET_ONLY`: audit only the dotnet stack; the Node.js stack records `NOT_RUN + reason`.
  - `NODE_ONLY`: audit only the Node.js stack; the dotnet stack records `NOT_RUN + reason`.
- `output_root`: full-stack output root directory, defaulting to `{dotnet_source_path}_fullstack_audit`.
- `coverage_mode`: `FULL | SAMPLE | INCREMENTAL`, defaulting to `FULL`, passed through to both sub-pipelines to take effect respectively.

Derived variables (used to align full-stack artifacts):

- `project_name`: extracted from the `dotnet_source_path` directory name (basename).
- `timestamp` / `run_timestamp`: the unified full-stack generation timestamp, canonical name `run_timestamp`, recommended format `YYYY_MM_DD_HH_mm`. Generated by the orchestration layer and issued to both sub-pipelines; all artifact naming in both stacks uniformly uses `run_timestamp`, and sub-stacks generating their own timestamps independently is forbidden; the difference between a sub-stack's actual start time and `run_timestamp` is only registered in the mapping table of each `quality/manifest_*.md` (the standard source of truth see the naming section of `IO_PATH_CONVENTION.md`).
- `run_id`: recommended `{project_name}_{timestamp}` or an equivalent unique identifier, used throughout this execution.

Global constraints (reiterated in the body):

- **GC1 Pure-documentation constraint**: this skill and this task may only create/modify `.md` files; creating `scripts/` or any executable code file is forbidden. This skill, in its current installation form, is a "documentation orchestration / methodology" version; if no corresponding executor exists in the environment, proceed directly with the staged processes for source analysis and report generation.
- **GC6 Exclusion rule**: during Node.js-side enumeration, `node_modules/`, `dist/`, `build/`, `.next/`, `.nuxt/`, and `coverage/` directories are not included in the audit surface; `package-lock.json`/`yarn.lock`/`pnpm-lock.yaml` are lockfile exceptions and must be included in the supply chain audit; **exception (2026-09-18)**: embedded foreign-stack projects are outside the GC6 exclusion scope and are handled per the phase 0 ownership decision table.

## Phase 0: Dual-Stack Stack-Detect

Objective: identify the dual-stack tech stacks and entry forms, providing the basis for subsequent adapter selection, framework specialty triggering, and coverage wording adjustments.

1. **Node.js stack detection**
   - Attribution: the node-side stack-detect is completed by the built-in phase 0 of `node-audit-pipeline` (there is no standalone node-stack-detect skill under skills/); the full-stack layer does not invoke it itself, and reads `{output_root}/node/stack_detect/stack_detect_{timestamp}.md` as the node stack basis, avoiding dual sources for the same artifact.
   - Input (consumed by the built-in phase 0 of node-audit-pipeline): `node_source_path/package.json`.
   - Artifact read: `{output_root}/node/stack_detect/stack_detect_{timestamp}.md`.
   - When reading, confirm the artifact content essentials: Web/SSR/GraphQL framework surfaces, build tools, SPA degradation markers, GC6 exclusion rule effectiveness statement, and the embedded foreign-stack project ownership decision table; **when the artifact is missing, no longer silently fall back** to reading the node-side route_mapping entry form summary — that stack's phase 0 must be set to `BLOCKED` and written into the full-stack manifest `gate_reason` (stating the missing item); re-read it only after node-audit-pipeline backfills `stack_detect_{timestamp}.md`, then phase 1 may continue.

2. **dotnet stack/framework surface identification**
   - There is no standalone `dotnet-stack-detect` skill on the dotnet side; the built-in phase 0 of `dotnet-audit-pipeline` completes stack and framework surface identification and mandatorily delivers `stack_detect/stack_detect_{timestamp}.md`.
   - The full-stack layer reads `{output_root}/dotnet/stack_detect/stack_detect_{timestamp}.md` as the dotnet stack basis; **when the artifact is missing, no longer fall back** to reading `framework_audit/` framework identification conclusions or route_mapping entry form summaries as equivalent artifacts — it must be set to `BLOCKED` and written into the full-stack manifest `gate_reason` (stating the missing item), and re-read after backfill.

3. **Single-stack mode handling**
   - When `stack_mode=DOTNET_ONLY`, the Node.js side creates `{output_root}/node/stack_detect/empty_result_{timestamp}.md`, stating `execution_status=NOT_RUN` with reason=`stack_mode=DOTNET_ONLY`.
   - When `stack_mode=NODE_ONLY`, the dotnet side must create `{output_root}/dotnet/stack_detect/empty_result_{timestamp}.md`, stating `execution_status=NOT_RUN` with reason=`stack_mode=NODE_ONLY`.

4. **Embedded foreign-stack project detection (2026-09-18)**: when the node repository hits `*.csproj`/`*.sln`/`*.fsproj` outside the GC6 exclusion directories, or the dotnet repository hits a `package.json` referenced by build scripts or a `src/web/` frontend directory → the stack-detect artifact must contain a "## Embedded Foreign-Stack Projects" section, registering each item by the three states of the ownership decision table (sample: audit with the host and annotate "sample" / production reference: promote to an independent audit surface and schedule the corresponding stack pipeline / documentation only: exclude and record the reason; leaving blank is not allowed). Three-state criteria — sample: the path contains sample/demo/example or the manifest declares it as an example, and its findings are registered the same as real code (sample private keys are also registered); production reference: the host code actually references its build artifacts/routes/packages, promote it to an independent audit surface; documentation only: no build artifacts and no host references, exclude and record the reason.

Phase 0 outputs:

- `{output_root}/node/stack_detect/stack_detect_{timestamp}.md`
- `{output_root}/dotnet/stack_detect/stack_detect_{timestamp}.md` or `empty_result_{timestamp}.md` (mandatory artifact; if missing, set BLOCKED and state the missing item)
- Phase 0 marked as `DONE` in `{output_root}/quality/manifest_{run_id}.md`

**Intent-source recursive probing (2026-09-18)**: when the full-stack orchestration layer issues design_intent artifacts in phase 0.7, negative conclusions must carry the complete `search_scope` self-evidence; the sub-pipelines' re-check disagreement reports must be written into the full-stack manifest `gate_reason` and block that stack's phase 1 until corrected.

## Dual-Stack Parallel Scheduling (Mandatory)

Objective: drive both sub-pipelines in parallel through directory isolation without any modification to the `dotnet-audit-pipeline` body.

1. **Directory isolation principle**
   - `dotnet-audit-pipeline` is invoked with `output_path={output_root}/dotnet`, and all its artifacts fall into the `{output_root}/dotnet/` subtree.
   - `node-audit-pipeline` is invoked with `output_path={output_root}/node`, and all its artifacts fall into the `{output_root}/node/` subtree.
   - Explicit declaration: the `dotnet-audit-pipeline` body has zero changes; full-stack directory isolation is achieved only through the `output_path` parameter.

2. **Parameter pass-through**
   - Each stack receives:
     - `source_path` = `dotnet_source_path` / `node_source_path`
     - `output_path` = `{output_root}/dotnet` / `{output_root}/node`
     - `coverage_mode` (same as the full-stack layer)
   - The sub-pipelines internally generate their own `run_id`-equivalent identifiers or reuse the full-stack `run_id`, but must record the mapping to the full-stack `run_id` in their respective `quality/manifest_*.md`.

3. **Parallel execution**
   - Logically schedule both sub-pipelines in parallel; actual concurrency is determined by the execution environment.
   - When either sub-pipeline is `BLOCKED`, the full-stack layer `pipeline_execution` must not be marked as `COMPLETED`.

4. **Single-stack mode handling**
   - When `stack_mode=DOTNET_ONLY`, `node-audit-pipeline` is not invoked; the Node.js subtree records the `NOT_RUN` reason via an empty-result statement file.
   - When `stack_mode=NODE_ONLY`, `dotnet-audit-pipeline` is not invoked; the dotnet subtree records the `NOT_RUN` reason via an empty-result statement file.

Phase 1–5 artifacts are produced by each sub-pipeline respectively; the full-stack layer only reads them and does not interfere:

- `{output_root}/dotnet/route_mapping/routes_{timestamp}.md`
- `{output_root}/dotnet/quality/api_coverage_gate_{timestamp}.md`
- `{output_root}/node/route_mapping/routes_{timestamp}.md`
- `{output_root}/node/quality/api_coverage_gate_{timestamp}.md`
- and each stack's `route_tracer/`, `vuln_audit/`, `vuln_poc/`, `framework_audit/`, `exploit_chain/`, `quality/`, and all other artifacts.

**Milestone write-back (mandatory, replacing polling)**:
- Each time a sub-pipeline completes a phase, a milestone line must be appended to its `quality/manifest_{run_id}.md`; the format is governed solely by `skills/shared/PHASE_STATUS.md`.
- The orchestration layer waits via "sub-pipeline completion report" triggers + a one-time final-state verification of manifest milestones and key artifacts; periodic disk polling in the form of "scheduled sleep + file counting" is forbidden.
- Timeout fallback: only when no report is received beyond the expected duration is one active check allowed, with the check reason recorded in the manifest. The expected-duration standard is governed solely by `skills/shared/PHASE_STATUS.md`: FULL mode `estimated minutes = 2 + permille of total files × 8` (about 8 minutes per thousand files).

**0.7 re-check report**: the sub-pipelines' `design_intent_recheck` milestone line format — `Phase 0.7 Re-check: AGREE ({hit count}) | {timestamp}` or `Phase 0.7 Re-check: MISMATCH ({hit directory count}) | {timestamp}` (on MISMATCH, the orchestration layer must correct the design_intent artifacts and re-issue them; continuing with the error is forbidden). Format source of truth: PHASE_STATUS.md.

## Phase 6: Cross-Stack Correlation

Objective: reconcile frontend/BFF outbound calls against the dotnet backend route list for cross-stack contract reconciliation, identifying hidden attack surfaces and ghost calls.

**Execution order (mandatory, 2026-09-18)**: the P1 contract-mapper goes first — its artifacts `api_contract_map_{timestamp}.md` and `contract_coverage_gate_{timestamp}.md` must be persisted and verified before item 3's cross-stack-taint-linker and cross-stack-consistency-audit may start; the input sections of the latter two must explicitly list the contract_map artifact paths. If an abnormal interruption causes consistency-audit to start while contract_map is missing: it is allowed to first persist with "input missing", but the full-stack coverage_consistency_check must consume and backfill a second time (reading the later-arriving contract_map to update conclusions), and the backfill action is recorded in the manifest.

1. **P1 mandatory: cross-stack-contract-mapper**
   - Invoke: `cross-stack-contract-mapper`.
   - Inputs:
     - `{output_root}/dotnet/route_mapping/routes_{timestamp}.md`
     - `{output_root}/dotnet/route_mapping/params_{timestamp}.md`
     - `node_source_path`
     - `{output_root}/node/stack_detect/stack_detect_{timestamp}.md`
     - reverse proxy / baseURL environment variable evidence (optional; if present, the source must be recorded)
   - Outputs (persisted to `{output_root}/cross/` per `IO_PATH_CONVENTION.md`):
     - `{output_root}/cross/api_contract_map_{timestamp}.md` (matched / frontend_only / backend_only three buckets)
     - `{output_root}/cross/contract_coverage_gate_{timestamp}.md` (including `contract_coverage_status`)
     - `{output_root}/cross_analysis/index_{timestamp}.md` (phase index)

1.5 **node-feature-api-mapper (P1.5, 2026-09-19)**
   - Invoke: `node-feature-api-mapper` (when present under skills/; if absent, record NOT_RUN + reason).
   - Inputs: `node_source_path`, `{output_root}/node/route_mapping/routes_{timestamp}.md`, `{output_root}/node/route_mapping/frontend_outbound_{timestamp}.md`, the P1 artifact `{output_root}/cross/api_contract_map_{timestamp}.md` (matched bucket), `{output_root}/node/design_intent/` (optional).
   - Outputs: `{output_root}/node/route_mapping/feature_api_map_{timestamp}.md` (+ `unmapped_feature_calls_{timestamp}.md` when PARTIAL).
   - Semantics: view-layer reference, forbidden as an EVID evidence source; `coverage_status` does not affect the phase 6 completion state, but when PARTIAL it is written as a gate_reason remark.

2. **backend_only hidden attack surface handling**
   - `backend_only` entries must be written into high_risk_routes or the sampled variant under `{output_root}/dotnet/cross_analysis/`, as hidden attack surfaces preferentially entering the dotnet route-tracer.
   - **Trace attribution (2026-09-20)**: route traces for hidden attack surface (backend_only) entries are **executed directly by the orchestration layer** — when phase 6 executes, the dotnet sub-pipeline may have already exited, and falling back to requiring the sub-pipeline to restart and backfill is forbidden because of this; trace quality thresholds are consistent with and not lower than those inside the sub-pipeline: each trace must contain `file:line` evidence and a trace completeness statement, and the trace contract sections (Sink Summary / Parameter Controllability Matrix / Sink Location / Trace Completeness Statement / Sink Evidence Type Checklist) must be complete section by section per the `dotnet-route-tracer` template.
   - File selection follows the rules of `IO_PATH_CONVENTION.md`: when the dotnet side `api_coverage_status=COMPLETE`, write into `high_risk_routes_{timestamp}.md`; when `api_coverage_status=PARTIAL` or `coverage_mode=SAMPLE`, write into `sampled_high_risk_routes_{timestamp}.md`.
   - List all of them item by item in `2.2) Hidden Attack Surface List` of the final report, and `contract_backend_only_count` must equal the total number of list entries.

3. **Cross-stack trio (taint-linker and consistency-audit, ACTIVE; started depending on the P1 contract_map artifacts)**
   - Invoke `cross-stack-taint-linker`: input `contract_map`, output `{output_root}/cross/cross_taint_links_{timestamp}.md` (cross_taint_links), with XTRACE chains aggregated into `{output_root}/cross/exploit_chain/cross_stack_exploit_chains_{timestamp}.md`.
   - Invoke `cross-stack-consistency-audit`: output `{output_root}/cross/consistency_findings_{timestamp}.md` (consistency_findings), as a supplement for the full-stack layer's coverage_consistency_check.
   - The `linker_status` of `cross_stack_exploit_chains_{timestamp}.md` is updated from `NOT_EXECUTED` to `EXECUTED`.

Phase 6 outputs:

- `{output_root}/cross/api_contract_map_{timestamp}.md`
- `{output_root}/cross/contract_coverage_gate_{timestamp}.md`
- `{output_root}/cross/cross_taint_links_{timestamp}.md`
- `{output_root}/cross/consistency_findings_{timestamp}.md`
- `{output_root}/cross/exploit_chain/cross_stack_exploit_chains_{timestamp}.md` (formal cross-stack exploit chain artifact; when there are no cross-stack chains, record `NOT_APPLICABLE` with `empty_result_{timestamp}.md`)
- `{output_root}/cross_analysis/index_{timestamp}.md`

## Full-Stack Gates and Four Completion-State Declarations (Mandatory)

Objective: on top of the sub-pipelines' individual completion states, aggregate into a unified full-stack four completion-state declaration; replacing them with a single "completed" is forbidden.

1. **Four completion-state declaration fields (verbatim, must not be rewritten)**
   - `dotnet_api_coverage_status`: from `{output_root}/dotnet/quality/api_coverage_gate_{timestamp}.md`, value `COMPLETE | PARTIAL`.
   - `node_api_coverage_status`: from `{output_root}/node/quality/api_coverage_gate_{timestamp}.md`, value `COMPLETE | PARTIAL`.
   - `contract_coverage_status`: from `{output_root}/cross/contract_coverage_gate_{timestamp}.md`, value `COMPLETE | PARTIAL`.
   - `audit_surface_status`: full-stack vulnerability/framework specialty coverage status, value `COMPLETED | PARTIAL | INITIAL_SCREENED`.
   - `audit_surface_status` aggregation rule: aggregate by the weaker of the two sub-pipelines' individual `audit_surface_status` (from their respective `quality/manifest_*.md` or final reports) — if either is `PARTIAL` → `PARTIAL`; if both stacks are `COMPLETED` → `COMPLETED`; if either is `INITIAL_SCREENED` and none is `PARTIAL` → `INITIAL_SCREENED`. The weaker source must be noted in `gate_reason` (e.g. `dotnet_audit_surface_status=PARTIAL source`).
   - Preconditions for `audit_surface_status=COMPLETED`: the cross-stack chain artifact `cross/exploit_chain/cross_stack_exploit_chains_{timestamp}.md` has been generated (when there are no cross-stack chains, record NOT_APPLICABLE with `empty_result_{timestamp}.md`); when chains exist but contain `Inferred Feasible / Theoretically Feasible` links, `audit_surface_status` must not be higher than `PARTIAL`.

2. **Full-stack-level coverage gate summary (recommended to be written into `{output_root}/quality/fullstack_gate_{timestamp}.md` and final report `2) Coverage Gate Summary`)**
   - `dotnet_api_coverage_percent`
   - `node_api_coverage_percent`
   - `pipeline_execution`: `COMPLETED | PARTIAL`. The determination standard differs by `coverage_mode`:
     - `coverage_mode=FULL`: `COMPLETED` is allowed only when all four declarations are `COMPLETE`/`COMPLETED` and there is no `BLOCKED`.
     - `coverage_mode=INCREMENTAL`: when both sub-pipelines' individual `api_coverage_status=COMPLETE` (100% coverage within the changed set including expanded call chains, aligned with the gate standards of `node-audit-pipeline` and `IO_PATH_CONVENTION.md`), all four declarations are `COMPLETE`/`COMPLETED` and there is no `BLOCKED`, `COMPLETED` is allowed; and the full-stack final report must declare `coverage_mode=INCREMENTAL`, the incremental baseline (changed commit range), affected file count / total file count, and cite both stacks' `quality/incremental_scope_{timestamp}.md` and `unmapped_routes_{timestamp}.md` artifacts; wording such as "full audit complete" is forbidden.
     - `coverage_mode=SAMPLE`: `pipeline_execution` must not be `COMPLETED`; the highest is `PARTIAL`.
   - `gate_decision`: `ALLOW_COMPLETED | FORCE_PARTIAL`. Determination conditions: all four declarations are `COMPLETE`/`COMPLETED` and meet the current `coverage_mode` gate (`FULL` full coverage; `INCREMENTAL` 100% coverage within the changed set with the incremental baseline declaration completed) → `ALLOW_COMPLETED`; otherwise → `FORCE_PARTIAL`.
   - `gate_reason`: when `FORCE_PARTIAL`, state the specific blocking sources — which of the four declarations is specifically `PARTIAL`, which sub-pipeline is `BLOCKED`, `coverage_mode=SAMPLE`, or under INCREMENTAL the changed set not being fully covered; also note the weaker source of `audit_surface_status`.
   - `unmapped_routes_source`: the actual path of `{dotnet|node}/quality/unmapped_routes_{timestamp}.md`; if neither stack is `PARTIAL`, write `N/A`.

3. **Cross-stack contract coverage summary (final report `2.1)`)**
   - `contract_coverage_percent`, `contract_matched_count`, `contract_frontend_only_count`, and `contract_backend_only_count` must directly cite the three-bucket counts in `{output_root}/cross/contract_coverage_gate_{timestamp}.md`.
   - `contract_map_source` must not be `N/A`; if `contract_coverage_status=PARTIAL`, it must point to the actual artifact or the backfill plan of `{output_root}/cross/api_contract_map_{timestamp}.md`.
   - The reconciliation standard when `coverage_mode=INCREMENTAL`: reconcile only the frontend/backend calls involved in the changed set (changed file set + expanded affected call chains); `contract_coverage_percent` is computed with the frontend/backend calls within the changed set as the denominator; if the changed set involves no cross-stack calls, the reconciliation scope limitation and reason must be explicitly declared in `{output_root}/cross/contract_coverage_gate_{timestamp}.md`, and mixing with the FULL full-reconciliation standard is forbidden.

4. **Block linkage rules**
   - When `dotnet_api_coverage_status != COMPLETE` or `node_api_coverage_status != COMPLETE` or `contract_coverage_status != COMPLETE`, `pipeline_execution` must not be `COMPLETED`.
   - When `coverage_mode = SAMPLE`, `pipeline_execution` must not be `COMPLETED`.
   - When `coverage_mode = INCREMENTAL`, if either stack's `api_coverage_status != COMPLETE` within the changed set (including expanded call chains), `pipeline_execution` must not be `COMPLETED` (the difference from FULL lies in the coverage scope, not the determination logic).
   - Replacing the four completion-state declarations with a single "audit complete" statement is forbidden.

## Closing Double-Safety (Mandatory)

Objective: at the full-stack layer, execute once more consistency check → quick validation → exploit chain aggregation → final report → closing anchor checklist, ensuring cross-stack field alignment and BLOCKED linkage taking effect.

1. **Pending evidence pool aggregation (first, 2026-09-18)**: scan the "## Pending Evidence Pool for This File" sections of all artifacts, aggregate and generate `{output_root}/quality/pending_pool_{timestamp}.md` (including `pool_total`, aggregation time, and source list); the final report risk pool section cites only this file.

2. **Full-stack consistency check (consistency_check)**
   - Generate `{output_root}/quality/coverage_consistency_check_{timestamp}.md`.
   - The check scope includes at least:
     - `dotnet_api_coverage_status` / `node_api_coverage_status` / `contract_coverage_status` / `audit_surface_status` are consistent among the gate, cross/contract_coverage_gate, and the final report.
     - The `contract_map` three-bucket counts (`matched_count`/`frontend_only_count`/`backend_only_count`) are consistent with the final report `2.1)` counts.
     - The exploit-chain overview table statistics are consistent with the final report `exploit_chain_consistency_check_counts`.
   - Output `consistency_check_status`: `PASS | BLOCKED`.

3. **Quick validation (quick_validation)**
   - Generate `{output_root}/quality/quick_validation_{timestamp}.md`.
   - `quick_validation.final_decision` must be linked with `consistency_check_status`: if `consistency_check_status=BLOCKED`, then `final_decision` must be `BLOCKED`.

4. **Exploit chain aggregation (exploit_chain)**
   - Generate `{output_root}/exploit_chain/exploit_chains_{timestamp}.md`, aggregating the single-stack exploit chains already produced by both sub-pipelines, and passing through `coverage_mode`, `api_coverage_status`, and other coverage wording.
   - Generate `{output_root}/cross/exploit_chain/cross_stack_exploit_chains_{timestamp}.md` (formal artifact): aggregate the XTRACE chains of `cross-stack-taint-linker`, annotating `feasibility` per chain in three grades (Confirmed Feasible / Inferred Feasible / Theoretically Feasible); when there are no cross-stack chains, record `NOT_APPLICABLE` with `empty_result_{timestamp}.md`.
   - If `consistency_check_status=BLOCKED`, exploit-chain feasibility must not be marked as "Confirmed Feasible".

5. **Final report (final_report)**
   - Generate `{output_root}/{project_name}_code_audit_{timestamp}.md`.
   - The quality section must reuse the fixed fields of `skills/shared/FULLSTACK_FINAL_REPORT_FIXED_TEMPLATE.md`.
   - It must include the four completion-state declarations, the cross-stack contract coverage summary, the hidden attack surface list, cross-stack exploit chains, the consistency check summary, and references to the closing anchor check results.
   - When `coverage_mode=INCREMENTAL`, the final report must declare the incremental baseline and coverage scope: `coverage_mode=INCREMENTAL`, the change baseline (commit range), affected file count / total file count, and cite both stacks' `quality/incremental_scope_{timestamp}.md` / `unmapped_routes_{timestamp}.md` artifacts; wording such as "full audit complete" is forbidden.

6. **Closing anchor checklist (final_anchor_checklist)**
   - Generate `{output_root}/quality/final_anchor_checklist_{timestamp}.md`.
   - Beyond the dotnet and node sub-pipeline anchor rows, cross-stack anchor rows must be added:
     - [ ] The three-bucket counts of `cross/api_contract_map_{timestamp}.md` reconcile with the final report `2.1)` counts.
     - [ ] The `contract_coverage_status` of `cross/contract_coverage_gate_{timestamp}.md` is confirmed.
   - Summary block:
     - `checklist_pass_count`
     - `checklist_blocked_count`
     - `checklist_pending_count`
     - `final_anchor_decision`: `PASS | BLOCKED | PENDING`
   - If `checklist_blocked_count > 0`, `final_anchor_decision` must be `BLOCKED`.
   - The final report `4.6)` fields must align field by field with the checklist summary block.

Constraints:

- All empty results or unexecuted phases must create an `index_{timestamp}.md` or `empty_result_{timestamp}.md` stating the `NOT_RUN` reason; missing directories are forbidden.
- The final report must declare `dotnet_api_coverage_status`, `node_api_coverage_status`, `contract_coverage_status`, and `audit_surface_status` simultaneously; replacing them with a single "completed" is forbidden.
- Full-stack unified `run_timestamp`: all `{timestamp}` artifact names in this directory tree (the `dotnet/`, `node/`, `cross/`, `quality/` subtrees and the full-stack final report) uniformly use the `run_timestamp` issued by the orchestration layer to both sub-pipelines; differences in sub-stack actual start times are only registered in their respective `quality/manifest_*.md` mapping tables, and introducing a second timestamp for naming artifacts is forbidden (source of truth see the naming section of `IO_PATH_CONVENTION.md`).
